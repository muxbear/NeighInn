## 1. 需求解读与术语统一

### 1.1 需求原文要点

1. 「社区业主」维护小区住户信息。
2. 可选定一个社区住户，授予「角色权限」中配置的某个角色（例如「社区管理员」），使其成为后台系统用户，具备该角色权限并可登录管理端。
3. 「用户管理」维护的是可登录移动端的 C 端用户，这些用户可以是某个小区的住户。
4. 需要分析后台数据库结构设计与优化，并给出业务逻辑实现方案。

### 1.2 术语

| 术语 | 对应实体 | 说明 |
| --- | --- | --- |
| C 端账号 | `users` | 手机号唯一，登录移动端，承载交易、社交、认证等 C 端行为 |
| 住户档案 | `residents` | 社区维度的人员档案，`user_id` 可空；同一用户在同一社区应仅一条有效档案 |
| 后台身份 | `admin_users` | 后台登录凭证 + 角色 + 社区数据范围的载体，当前是独立账号体系（D-05） |
| 后台角色 | `roles` | 角色权限页维护，含 `data_scope` |
| 社区数据范围 | `admin_user_communities` | 后台身份可操作的社区集合，`OWN_COMMUNITY` / `COMMUNITY_SET` 依赖它 |

### 1.3 核心结论

**后台身份不应是「第二个人」，而应是挂在 C 端账号上的一项授权。**

推荐保留 `admin_users` 作为独立凭证与权限容器（不破坏现有登录、审计、历史外键），新增 `admin_users.platform_user_id` 与 `users.id` 的 1:0..1 关联，并用 `admin_users.resident_id` 记录授权来源住户。这样：

- 同一个人只有一份 C 端身份；
- 后台登录凭证仍与 C 端 JWT 隔离，符合 D-05；
- 住户被授权后不是复制一份人员信息，而是给已有账号追加后台能力；
- 撤销授权只影响后台身份，不影响移动端使用。

### 2.2 问题清单

| 编号 | 问题 | 影响 |
| --- | --- | --- |
| P-01 | `admin_users` 与 `users` 无任何关联 | 住户无法被授权；同一人可能在两套体系重复存在 |
| P-02 | `residents.user_id` 可空，注册时不会回填 | 住户先建档、后注册时，档案与账号永久脱节 |
| P-03 | 「用户管理」页维护的是后台账号，不是 C 端用户 | 与需求语义相反；C 端 `/users` 接口虽存在但前端未使用 |
| P-04 | `Role.data_scope` 仅在工作台接口生效 | 一旦把社区角色授予住户，等于让其看到全平台数据，属于安全红线 |
| P-05 | `get_permission_codes` 未过滤 `Role.status` | 已停用角色仍会授予权限 |
| P-06 | `GET /residents`、`GET /residents/{id}` 等读接口未挂权限依赖 | 任意后台会话可读取全部社区住户 |
| P-07 | 住户列表逐行查询社区/用户/认证/后台信息 | 新增后台身份字段后 N+1 进一步放大 |
| P-08 | 后台账号创建密码策略 6 位，修改密码策略 12 位 | 策略不一致，初始密码强度不足 |
| P-09 | 2FA 仅在 `two_factor_enabled` 时触发 | 新账号默认不强制绑定，敏感角色存在风险 |
| P-10 | 撤销后台权限后旧 Cookie 会话仍存活 | 只要账号重新启用，旧会话可能“复活” |

## 3. 方案选型

### 3.1 候选方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. 物理合并账号 | 把 `users` 与 `admin_users` 合为一张账号表 | 模型最纯粹 | 46+ 张表引用 `admin_id`/`user_id`，审计、会话、历史数据迁移量巨大；登录契约需重写 | 本期不做 |
| B. 后台身份关联 C 账号 | `admin_users` 增加 `platform_user_id`（唯一）、`resident_id`（来源） | 增量改造、兼容存量、可快速上线；保留独立凭证体系 | 仍有两张账号表，需要同步规则 | **推荐** |
| C. 独立授权关系表 | 新增 `admin_grants` 记录住户→角色 | 可表达多段授权历史 | `admin_users` 仍需存在，多一层 join，1:1 场景收益低 | 不采用 |

### 3.2 选择 B 的理由

1. **兼容存量**：现有后台账号 `source='MANUAL'`，`user_id` 为 NULL，无需回填。
2. **安全边界清晰**：C 端 JWT 与后台 Cookie 会话继续隔离；后台密码、2FA、锁定策略不变。
3. **可撤销**：撤销的是 `admin_users` 上的角色与状态，不动 `users`。
4. **可演进**：未来若要做统一身份/SSO，`user_id` 就是现成的迁移锚点。

## 4. 数据库结构设计

### 4.1 目标关系

```text
users 1 ──── 0..1 admin_users        (platform_user_id 唯一；一个人最多一个后台身份)
users 1 ──── 0..n residents          (user_id；同一社区唯一)
residents 1 ─ 0..1 admin_users       (resident_id 仅记录授权来源)
admin_users n ─ n roles
admin_users n ─ n communities        (数据范围)
roles n ─ n permissions
```

### 4.2 `admin_users` 表变更

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| `platform_user_id` | BIGINT | NULL，FK `platform_users.id`，**唯一** | 关联 C 端平台账号；存量手工账号为 NULL |
| `resident_id` | BIGINT | NULL，FK `residents.id`，索引 | 授权来源住户；手工账号为 NULL |
| `source` | VARCHAR(16) | NOT NULL DEFAULT `'MANUAL'` | `MANUAL`（后台手工创建）/ `RESIDENT`（住户授权） |
| `must_change_password` | BOOLEAN | NOT NULL DEFAULT false | 首次登录/重置后强制改密 |
| `session_version` | INTEGER | NOT NULL DEFAULT 0 | 会话版本；撤销、停用、重置密码时自增，用于立即失效旧会话 |
| `password_updated_at` | TIMESTAMP | NULL | 最近改密时间（可选，便于审计） |

> 说明：`admin_users.phone_enc` 对 `source='RESIDENT'` 的账号不再重复写入，读取时回退到关联 `users.phone_enc`，减少 PII 重复存储。手工账号保持原样。

### 4.3 `roles` 表变更

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| `assignable_to_resident` | BOOLEAN | NOT NULL DEFAULT false | 是否允许在「社区业主」页授予该角色 |

**双重约束**：只有同时满足以下条件的角色才能授予住户：

1. `roles.status = 'ACTIVE'`
2. `roles.assignable_to_resident = true`
3. `roles.data_scope = 'OWN_COMMUNITY'`
4. `roles.code != 'super_admin'`

仅靠 `data_scope` 不够：自定义的 `OWN_COMMUNITY` 角色也可能包含资金或系统权限。`assignable_to_resident` 提供显式白名单，避免误授权。

### 4.4 索引与约束优化

```sql
-- 一个人最多一个后台身份
CREATE UNIQUE INDEX uq_admin_users_platform_user_id ON admin_users (platform_user_id);
CREATE INDEX ix_admin_users_resident_id ON admin_users (resident_id);

-- 角色成员统计与社区管理员查询
CREATE INDEX ix_admin_user_roles_role_id ON admin_user_roles (role_id);
CREATE INDEX ix_admin_user_communities_community_id ON admin_user_communities (community_id);

-- 同一社区同一账号仅一条有效住户档案（先清理重复数据再建）
CREATE UNIQUE INDEX uq_residents_community_user
  ON residents (community_id, user_id) WHERE user_id IS NOT NULL;

-- 住户列表常用过滤
CREATE INDEX ix_residents_community_identity
  ON residents (community_id, identity_type);
CREATE INDEX ix_residents_community_cert
  ON residents (community_id, certification_status);
CREATE INDEX ix_residents_community_status
  ON residents (community_id, status);
```

> PostgreSQL 与 SQLite 对 NULL 的处理一致：唯一索引允许多个 `user_id IS NULL`，存量手工账号不受影响。

### 4.5 种子角色与权限

新增内置角色：

| 字段 | 值 |
| --- | --- |
| `code` | `community_admin` |
| `name` | 社区管理员 |
| `description` | 负责本社区内容运营、住户服务与审核 |
| `data_scope` | `OWN_COMMUNITY` |
| `is_builtin` | true |
| `assignable_to_resident` | true |

新增权限码：

| 权限码 | 名称 | 分配给 |
| --- | --- | --- |
| `community:resident:admin-grant` | 授予住户后台角色 | `community_operator`、`super_admin` |
| `community:resident:admin-revoke` | 解除住户后台授权 | `community_operator`、`super_admin` |

> **默认不让 `community_admin` 拥有授予/解除权限**，避免社区管理员自行扩权。若产品要求社区自治，可后续显式配置。

`community_admin` 建议默认权限（可在角色权限页调整）：

```text
dashboard:view
community:broadcast:view/create/update/delete/review/offline
community:item:view/review/recommend/offline
community:help:view/review/match/close
community:life:view/create/update/delete/review/offline
community:maintenance:view
community:resident:view/create/update/audit/freeze
communication:notice:view/create/publish
communication:task:view/create/send
governance:report:view/handle
reporting:export:view
```

不包含：资金域、系统管理域、角色配置、`community:resident:revoke`、后台账号管理。

### 4.6 迁移脚本 `0011_resident_admin_link.py`

建议按以下顺序实现（沿用 `0004` / `0005` 的幂等风格）：

1. `_column_exists` 检查后 `op.add_column` 添加 `admin_users` 五个核心字段（`password_updated_at` 可选）、`roles.assignable_to_resident`。
2. 创建索引与唯一索引；创建部分唯一索引前先做重复数据检查，若存在冲突则中止并输出清单，禁止静默删除。
3. 插入 `community:resident:admin-grant`、`community:resident:admin-revoke` 权限。

5. 给 `community_operator` 补充两条新权限。
6. 将 `community_admin` 的 `assignable_to_resident` 置 true。
7. `downgrade` 反向删除索引、字段、权限；若角色已有成员则拒绝删除并给出提示。

- `web/backend/src/db/models/system.py`：`AdminUser`、`Role` 新字段，`admin_user_roles` / `admin_user_communities` 索引。

## 5. 业务逻辑设计

### 5.1 授权前置条件

在 `社区业主 → 授予后台角色` 时，服务端必须逐项校验：

| 条件 | 不满足时的处理 |
| --- | --- |
| 住户存在 | 40401 |
| `resident.status = 'ACTIVE'` | 42201「住户已停用/已离开，不能授予后台权限」 |
| `resident.certification_status = 'VERIFIED'` | 42201「住户认证未通过，不能授予后台权限」 |
| 手机号存在或已有 `user_id` | 42201「住户缺少手机号，无法创建移动端账号」 |
| 关联 `User.status = 'ACTIVE'` | 42201「移动端账号已冻结/注销」 |
| 角色 `status='ACTIVE'` 且 `assignable_to_resident=true` 且 `data_scope='OWN_COMMUNITY'` | 42201「该角色不允许授予社区住户」 |
| 同一 `user_id` 未绑定其他后台身份 | 若已存在，走「调整角色」而非重复创建 |
| 操作人具备 `community:resident:admin-grant` | 40301 |

### 5.2 授权流程

```text
操作人（社区运营/超管）
  └─ 社区业主列表 → 选择住户 → 授予后台角色
       ├─ 1. 校验权限、住户认证、账号状态
       ├─ 2. resident.user_id 为空？
       │     ├─ 按 phone_hash 查找 users
       │     └─ 未找到则创建 C 端账号（registration_channel='admin'）并回填 resident.user_id
       ├─ 3. 创建/更新 admin_users
       │     ├─ source='RESIDENT', resident_id=..., user_id=...
       │     ├─ username 默认 u{userId}，允许操作人修改
       │     ├─ 生成 12 位初始密码（仅哈希落库，明文仅返回一次）
       │     └─ must_change_password=true
       ├─ 4. 写 admin_user_roles（校验角色白名单）
       ├─ 5. 写 admin_user_communities（固定为 resident.community_id）
       ├─ 6. 写审计 + Outbox 事件
       └─ 7. 返回账号信息与初始密码（一次性展示）
```

**事务边界**：创建 C 端账号、创建后台账号、角色绑定、社区绑定、审计、Outbox 必须在同一事务内；任何一步失败全部回滚。

**并发控制**：`admin_users.platform_user_id` 唯一索引兜底；并发重复授权捕获 `IntegrityError` 并返回 40901「该住户已开通后台身份」。写接口必须带 `X-Idempotency-Key`（项目既有规则）。

### 5.3 登录与首登

1. 登录仍走 `POST /api/v1/admin/auth/login`，账号密码 + 可选 TOTP。
2. `admin_users.source='RESIDENT'` 的账号，登录时额外校验：
   - 关联 `users.status = 'ACTIVE'`；
   - `resident.status = 'ACTIVE'`；
   - `resident.certification_status` 不为 `FROZEN` / `REVOKED` / `LEFT`。
3. 登录响应新增：
   ```json
   {
     "admin": {
       "id": "9", "username": "u456", "realName": "张三",
       "source": "RESIDENT", "dataScope": "OWN_COMMUNITY",
       "communities": [{ "id": "1", "name": "阳光花园" }],
       "mustChangePassword": true
     },
     "csrfToken": "..."
   }
   ```
4. `must_change_password=true` 时，`get_current_admin` 对业务接口返回 `40306 首次登录需修改初始密码`，仅放行：
   - `/auth/me`
   - `/auth/password/change`
   - `/auth/logout`
   - `/auth/csrf`
5. 改密成功后：
   - `must_change_password=false`；
   - `password_updated_at` 更新；
   - `session_version += 1`，并刷新当前会话中的版本，其他旧会话失效。
6. 密码策略统一为 **至少 12 位，且包含大小写字母/数字/符号中的至少三类**，创建、重置、修改共用同一校验函数。
7. 2FA：
   - 本期沿用现有 TOTP 绑定流程；
   - 建议后续对 `source='RESIDENT'` 或含敏感权限的角色强制绑定后才可进入工作台；
   - 短信通道接入后，可改为手机号 + 短信验证码登录/二次验证。

### 5.4 数据范围落地（P0 安全前置）

当前 `allowed_community_ids()` 只在 `api/admin/dashboard.py` 使用。授予社区管理员之前，必须把范围过滤铺到所有社区域接口，否则等于授予全平台数据访问。

**实施模式**：

```python
# 列表：请求的 communityId 必须在允许集合内；未传则按允许集合过滤
async def resolve_community_scope(db, admin, requested: int | None) -> int | None | set[int]:
    allowed = await allowed_community_ids(db, admin)
    if allowed is None:
        return requested          # ALL
    if requested is not None:
        if requested not in allowed:
            raise ApiError(ERR_DATA_SCOPE, "数据范围越界", 403)
        return requested
    return allowed                # 空集合 → 返回空列表

# 详情/写操作：先取实体，再校验其 community_id
await assert_community_allowed(db, admin, resident.community_id)
```

**必须覆盖的接口**：

| 文件 | 接口/场景 |
| --- | --- |
| `api/admin/residents.py` | 住户列表/详情/新增/编辑/删除/批量删除/冻结/解冻/撤销/认证材料/认证审核队列/汇总 |
| `api/admin/operations.py` | 社区物品、生活内容、邻里互助、喇叭的列表与写操作 |
| `api/admin/communication.py` | 公告、通知任务的社区投放范围 |
| `api/admin/communities.py` | 社区运维列表、社区详情、编辑 |
| `api/admin/governance.py`、`governance_extra.py` | 举报、报修、投诉、纠纷的社区过滤 |
| `api/admin/users.py` | 若授予了 `system:user:view`，按住户所属社区过滤 |
| `api/admin/dashboard.py` | 已实现，保持 |

同时修复：

- `get_permission_codes` 增加 `Role.status == 'ACTIVE'` 过滤；
- `GET /residents`、`GET /residents/{id}`、`GET /residents/summary` 补 `community:resident:view` 权限依赖；
- `resident_summary` 的 `communityId` 默认值 `1` 改为从数据范围推导，禁止默认泄露 1 号社区数据；
- 前端社区切换器只展示 `/auth/me` 返回的 `communities`；`OWN_COMMUNITY` 时锁定不可切换。

### 5.5 状态联动

| 触发事件 | 后台身份处理 | 说明 |
| --- | --- | --- |
| `users.status` → `FROZEN` / `CANCELLED` | 关联后台账号 `status='DISABLED'`，`session_version += 1` | C 端停用/注销即失去后台能力 |
| `resident.status` → `FROZEN` / `LEFT` | 同上 | 住户资格失效 |
| `resident.certification_status` → `REVOKED` / `FROZEN` | 同上 | 认证资格失效 |
| 住户解冻/重新认证 | 不自动恢复后台权限 | 需重新授权，避免状态回弹导致权限意外恢复 |
| 角色被停用/删除 | 权限实时收敛 | 修复 `Role.status` 过滤；删除角色仍要求先移除成员 |
| 角色权限被修改 | 实时生效 | 权限每请求查库，无需刷新会话 |
| 后台账号被解除授权 | `status='DISABLED'`、清空角色、`session_version += 1` | 不物理删除，保留审计关联 |
| 住户档案被删除 | 若存在关联后台账号则拒绝删除 | 必须先解除授权，保证审计链完整 |
| 手工后台账号绑定 C 端账号 | 可选能力 | 用于员工本身也是住户的场景，本期可不做 |

**会话立即失效**：`get_current_admin` 从会话中取 `session_version`，与 `admin_users.session_version` 比对；不一致返回 401。撤销、停用、重置密码均自增版本，解决旧 Cookie 会话“复活”问题。

### 5.6 撤销授权

- 接口：`POST /residents/{resident_id}/admin-account/revoke`
- 动作：
  1. 删除 `admin_user_roles` 中该后台账号的角色；
  2. 删除 `admin_user_communities` 中由该住户授权带入的社区绑定；
  3. `admin_users.status='DISABLED'`、`must_change_password=true`、`session_version += 1`；
  4. 写审计 `resident.admin.revoke` 与 Outbox 通知；
  5. C 端账号与住户档案不受影响。
- 不物理删除 `admin_users`：`audit_logs.actor_id`、历史操作人展示需要保留。

### 5.7 C 端账号与住户联动

1. **注册回填**：在 `get_or_create_user_by_phone` 创建新用户后，按 `phone_hash` 回填 `residents.user_id IS NULL` 的档案；同时可回填同一手机号的认证单关联（如需要）。
2. **建档匹配**：`create_resident` / `update_resident` 已有按手机号匹配 `users` 的逻辑，保留并补测试。
3. **后台建号**：`POST /users` 由管理员创建 C 端账号时，同步按手机号绑定已有住户档案；`registration_channel='admin'`。
4. **手机号变更**：C 端换绑手机号后不自动改写住户档案手机号（住户联系方式与登录账号可能不同）；如需同步，单独提供运营操作并审计。
5. **隐私**：住户授权时创建的 C 端账号，其注册协议同意时间需在首次登录时补记，或在授权弹窗中提示操作人代为确认的合规风险。

### 5.8 审计、幂等与通知

| 动作 | 审计 action | Outbox 事件 | 幂等 |
| --- | --- | --- | --- |
| 授权/调整角色 | `resident.admin.grant` | `ResidentAdminGranted` | 必须 |
| 解除授权 | `resident.admin.revoke` | `ResidentAdminRevoked` | 必须 |
| 重置初始密码 | `resident.admin.reset-password` | 无 | 必须 |
| 自动创建 C 端账号 | `resident.user.create-and-link` | `ResidentUserLinked` | 随授权事务 |
| 状态联动停用 | `resident.admin.disable` | `ResidentAdminDisabled` | 系统事件 |

**安全要求**：

- 初始密码只返回一次，禁止写入审计 `after_snapshot`、Outbox payload、日志、`idempotency_keys.response_json`。
- 幂等重放时返回 `initialPassword: null` + `replay: true`，提示操作人使用「重置初始密码」重新生成。
- 通知内容只包含「已开通后台权限，请使用账号 xxx 登录」，不包含密码。
- 审计快照记录：`residentId`、`userId`、`adminId`、`roleCodes`、`communityIds`、`source`。

## 6. 接口设计

### 6.1 住户后台身份管理（管理端）

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/admin/residents/{resident_id}/admin-account` | `community:resident:view` | 查询该住户的后台身份 |
| POST | `/api/v1/admin/residents/{resident_id}/admin-account` | `community:resident:admin-grant` | 授权/调整角色 |
| POST | `/api/v1/admin/residents/{resident_id}/admin-account/revoke` | `community:resident:admin-revoke` | 解除授权 |
| POST | `/api/v1/admin/residents/{resident_id}/admin-account/reset-password` | `community:resident:admin-grant` | 重置初始密码 |
| GET | `/api/v1/admin/resident-admin-roles` | `community:resident:admin-grant` | 返回可授予住户的角色列表 |

**授权请求**：

```json
{
  "roleIds": [7],
  "username": "u456",
  "reason": "业主委员会推荐，负责本社区内容运营"
}
```

- `username` 可省略，默认 `u{userId}`；已存在且属于同一账号时可忽略。
- 初始密码由服务端生成，不接受前端传入，避免弱密码。
- `roleIds` 当前 UI 单选，接口保留数组以兼容多角色。

**授权响应（仅首次返回明文密码）**：

```json
{
  "code": 0,
  "message": "后台权限已开通",
  "data": {
    "admin": {
      "id": "9", "username": "u456", "realName": "张三",
      "status": "ACTIVE", "source": "RESIDENT",
      "roles": [{ "id": "7", "code": "community_admin", "name": "社区管理员" }],
      "communities": [{ "id": "1", "name": "阳光花园" }],
      "mustChangePassword": true
    },
    "initialPassword": "Abc123!@#xyz",
    "replay": false,
    "linkedUserCreated": true
  }
}
```

**查询响应**：

```json
{
  "code": 0,
  "data": {
    "residentId": "123",
    "userId": "456",
    "eligible": true,
    "eligibleReason": "",
    "account": {
      "id": "9", "username": "u456", "status": "ACTIVE",
      "source": "RESIDENT", "mustChangePassword": true,
      "roles": [{ "code": "community_admin", "name": "社区管理员" }],
      "communities": [{ "id": "1", "name": "阳光花园" }],
      "lastLoginAt": 0
    }
  }
}
```

不可授权时返回 `eligible=false` + `eligibleReason`（如「住户认证未通过」「缺少手机号」），前端据此禁用按钮。

### 6.2 住户列表增强

`GET /api/v1/admin/residents` 每行新增：

```json
{
  "adminAccount": {
    "id": "9", "username": "u456", "status": "ACTIVE",
    "roles": [{ "code": "community_admin", "name": "社区管理员" }],
    "mustChangePassword": true
  }
}
```

- 批量查询 `admin_users` + `admin_user_roles`，禁止逐行查询。
- `adminAccount` 为 `null` 表示未开通。

### 6.3 C 端用户管理接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/admin/users` | `system:user:view` | 新增 `communityId`、`hasResident`、`hasAdmin` 过滤 |
| GET | `/api/v1/admin/users/{id}` | `system:user:view` | 360° 详情增加全部住户档案、后台身份 |
| POST | `/api/v1/admin/users` | `system:user:create` | 管理员创建 C 端账号（手机号 + 昵称），自动绑定同手机号住户 |
| PUT | `/api/v1/admin/users/{id}` | `system:user:update` | 维护昵称/邮箱/简介（不直接改实名） |
| PATCH | `/api/v1/admin/users/{id}/status` | `system:user:update` | 停用/启用；停用时联动停用后台身份 |
| POST | `/api/v1/admin/users/{id}/penalties` | `system:user:penalty` | 既有处置；封禁联动后台身份停用 |

> 当前前端 `usersApi.create/update` 已声明但后端未实现，本次一并补齐，避免死接口。

### 6.4 登录接口增强

`POST /api/v1/admin/auth/login` 与 `GET /api/v1/admin/auth/me` 返回：

- `source`
- `dataScope`
- `communities`
- `mustChangePassword`
- `residentId`（有则返回）

新增错误码：

| 码 | 含义 |
| --- | --- |
| `40306` | 首次登录需修改初始密码 |
| `42205` | 该角色不允许授予社区住户（可选，复用 42201 亦可） |

### 6.5 角色接口增强

- `GET /api/v1/admin/roles` 返回 `assignableToResident`。
- `POST/PUT /api/v1/admin/roles` 接受并校验 `assignableToResident`；`dataScope != 'OWN_COMMUNITY'` 时禁止置 true。
- `GET /api/v1/admin/resident-admin-roles` 返回可授予角色（供社区业主页使用，无需 `system:role:view`）。

## 9. 迁移与发布步骤

### 9.1 发布顺序

1. **数据库迁移**：新增字段均为 NULL/有默认值，向后兼容；先执行 `0011`。
2. **种子同步**：`seed.py` 补角色与权限，保证测试与新库一致。

   - 模型与序列化；
   - 权限/角色接口；
   - 授权/撤销/重置接口；

5. **开关**：新增 `RESIDENT_ADMIN_ENABLED`（默认 false），数据范围过滤与安全测试通过后再开启。
6. **回归**：`uv run pytest -q`、`uv run ruff check`、`npm run typecheck`、`npm run build`、`scripts/smoke_e2e.py`。

### 9.2 存量数据

- 现有 `admin_users`：`source='MANUAL'`，`platform_user_id=NULL`，无需回填。
- `residents.user_id`：提供一次性脚本 `scripts/backfill_resident_user_links.py`，按 `phone_hash` 匹配并输出 dry-run 报告；确认后再写库。

### 9.3 回滚

- 关闭 `RESIDENT_ADMIN_ENABLED`，撤销入口立即失效；
- 已授权的住户后台账号可批量停用；
- 数据库字段可保留（不影响旧逻辑）；角色可保留但不再可授予；
- 回滚不删除审计记录。

## 13. 验收标准

1. 社区运营可在「社区业主」中为已认证住户授予「社区管理员」，系统生成后台账号并绑定该住户所在社区。
2. 住户使用该账号可登录管理端，首次登录强制改密，登录后仅能看到/操作本社区数据。

5. 所有授权/撤销/重置动作有审计记录，初始密码不以明文落库或写日志。
6. 既有手工后台账号、既有角色与社区绑定不受影响。

## 附录 A：为什么 `users` 不合并到 `residents`

### A.1 关系不是 1:1，而是 1:0..n

- `users` 是**平台级身份**：手机号唯一，承载登录、订单、消息、好友、钱包、信用等全平台行为。
- `residents` 是**社区级成员档案**：一个用户在一个社区一条档案；同一个人可以在多个社区各有档案。
- 注册发生在认证之前：用户可以先注册、浏览、选意向小区，尚未成为任何社区的住户。
- 物业可以代建档：没有手机号/没有 App 的老人、租户也可能先有住户档案，`user_id` 为空。

因此：

```text
1 个 users ── 0..n 个 residents
1 个 residents ── 0..1 个 users（可为空）
```

### A.2 四个真实场景会直接打破合并假设

| 场景 | `users` | `residents` | 合并后的问题 |
| --- | --- | --- | --- |
| 新用户注册，尚未认证 | 1 条 | 0 条 | 没有 `community_id`，只能造一条“半住户”记录，等于把 `users` 换个表名 |
| 物业代建档，老人无手机号 | 0 条 | 1 条 | 需要伪造登录行或允许密码为空，账号安全模型被破坏 |
| 同一人在 A、B 两个小区都有房 | 1 条 | 2 条 | 要么同一手机号两条登录记录（违反唯一），要么丢掉一个小区档案 |
| 用户注销，但住户档案需保留 | 1 条（匿名化） | 1 条（历史） | 账号生命周期与社区成员生命周期被混在一张表 |

### A.3 技术代价

1. **37 处外键直接引用 `users.id`**（`items.seller_id`、`orders.buyer_id/seller_id`、`wallet_accounts.user_id`、`ledger_entries`、`messages`、`friends`、`notifications`、`credit_logs`、`certifications.user_id` 等）。改为 `residents.id` 意味着全量数据迁移与所有查询重写。
2. **`residents` 行会被物理删除**：后台 `delete_resident` / `batch_delete_residents` 会删除档案。若订单、钱包、消息引用 `residents.id`，删档案会直接破坏历史数据。`users` 则只做冻结/注销匿名化，不物理删除。
3. **钱包与账本要求“一人一账”**：`wallet_accounts.user_id` 是唯一索引；若改用 `residents.id`，同一人在两个小区会有两个钱包，余额与流水被拆散。
4. **手机号唯一性冲突**：`users.phone_hash` 全局唯一；`residents.phone_hash` 只在社区内唯一（且可重复/为空）。合并后无法同时满足“一个手机号一个账号”和“一人多社区”。
5. **认证与审核链断裂**：`certifications` 同时引用 `user_id` 与 `resident_id`，审核通过后才建立 `resident`；合并会把“账号”和“审核结果”耦合在一起。

### A.4 合并必须接受的业务让步

如果坚持合并，产品必须同时接受：

- 一个手机号只能属于一个小区；
- 注册即必须完成住户建档，否则无法登录；
- 不允许物业代建档、不允许无手机号住户；
- 注销账号即删除/冻结住户档案与历史；
- 全平台订单、钱包、消息等历史数据重新迁移到新的身份主键。

这与当前 SRS 的注册引导、邻近小区、多社区、账号注销保留审计等规则冲突，不建议。

### A.5 如果目标是“减少重复”，推荐做法

1. **保持 `users` 为身份主表，`residents.user_id` 为强关联**（本次方案已采用）。
2. **明确字段归属**：
   - 登录手机号、密码/验证码、昵称、头像、协议留痕 → `users`；
   - 社区、楼栋、身份类型、认证状态、住户级别 → `residents`；
   - 档案无关联账号时，`residents.name` / `phone_enc` 作为联系方式快照保留。
3. **加约束防重复**：`(community_id, user_id)` 部分唯一索引。
4. **管理端用视图/批量装配消除查询重复**，而不是用物理合并消除表。
5. **可选**：把 `users.nickname` 与 `residents.name` 的展示关系明确为“账号昵称”和“档案姓名”，避免运营误以为重复。

### A.6 什么情况下才可以合并

只有当业务变成“**一人一小区、注册即建档、不允许代建档、不允许跨社区**”，并且愿意迁移全部 37 处身份外键时，才值得考虑把 `users` 与 `residents` 合并为一张“社区账号表”。当前产品形态不满足这些前提。

> 因此，本次改造采用「`users` 保持平台身份 + `residents` 保持社区档案 + `admin_users` 挂接授权」的三层模型，是对现有业务约束最稳妥的设计。

## 附录 B：表名评估——是否把 `users` 改名为 `community_users`

### B.1 结论

**技术上可以改，但不建议改，尤其不建议叫 `community_users`。**

`community_users` 会被理解为“社区内的用户/社区成员”，而真正表达社区成员关系的是 `residents`。把平台级账号命名为 `community_users`，会让“账号（跨社区）”“住户档案（社区内）”“后台账号（管理端）”三者的边界更模糊，而不是更清晰。

### B.2 改名的真实波及面

| 项目 | 数量/位置 |
| --- | --- |
| 模型表名 | `src/db/models/identity.py:16` 的 `__tablename__ = "users"` |
| 外键声明 | 37 处 `ForeignKey("users.id")`，分布在 content/engagement/funds/governance/identity/marketplace/notification/social/trade 等模型 |
| 历史迁移 | `0002`、`0004`、`0006`、`0010` 中存在 `"users"` 表名与 raw SQL；新迁移只需在链尾 rename，历史迁移保持原样 |
| 索引/约束/序列 | `ix_users_*`、`users_phone_hash_key`、`users_id_seq`、`users_*_fkey` 等名称不会随表名自动重命名，需要额外 `ALTER INDEX/CONSTRAINT/SEQUENCE ... RENAME` |
| 测试 | 测试用 `Base.metadata.create_all` 建表，遗漏的 FK 会在 mapper 配置/建表阶段直接报 `NoReferencedTableError`，可作为兜底 |
| 文档/脚本 | SRS、后台详设、本方案、README、`CLAUDE.md` 中的 `users` 表述需同步 |

一次 PostgreSQL `ALTER TABLE users RENAME TO community_users` 本身很快，但需要 `ACCESS EXCLUSIVE` 锁；旧代码与新表名不兼容，必须与后端发布同窗口进行，不能滚动升级。

### B.3 如果目的是消除 `users` 与 `admin_users` 的歧义

更推荐以下三种做法，而不是改 `users`：

1. **保留 `users`，把 `admin_users` 改名为 `admin_accounts`**：`users` 是行业通用叫法；`admin_users` 改为 `admin_accounts` 更能表达“后台登录账号”，且外键面远小于 `users`。
2. **只加数据库注释与文档术语**：
   ```sql
   COMMENT ON TABLE users IS '平台级 C 端账号（移动端登录身份，可关联 0..n 个社区住户档案）';
   COMMENT ON TABLE residents IS '社区住户档案（社区级成员关系，user_id 可空）';
   COMMENT ON TABLE admin_users IS '后台管理账号（独立凭证、角色与社区数据范围）';
   ```
3. **增加只读视图 `v_community_users`**：把 `users + residents + communities` 的常用展示字段拼好，供后台列表/报表使用。这样既得到“社区用户”的业务视图，又不动核心表。

### B.4 如果仍然决定改名

建议按以下步骤，避免遗漏：

1. 先确认没有生产流量或安排维护窗口；改名与代码发布必须同时进行。
2. 新增独立迁移 `0012_rename_users_table.py`：
   - `op.rename_table("users", "platform_users")`；
   - 重命名索引、唯一约束、外键约束、序列（可选但建议，保持命名一致性）；
   - `downgrade` 反向 rename。
3. 同步修改 37 处 `ForeignKey("users.id")` 与模型 `__tablename__`。
4. 跑 `Base.metadata.create_all` 相关测试，确保没有遗漏的外键目标。
5. 更新 seed、脚本、文档中的表名表述。
6. 验证 `uv run pytest -q`、`ruff check`、`scripts/smoke_e2e.py` 全部通过。

### B.5 推荐名称

**首选：`platform_users`（平台用户）**

理由：

1. 准确表达“平台级账号”，与社区级的 `residents` 区分；
2. 与 `admin_users` 形成“平台用户 / 后台用户”的清晰对照；
3. 不绑定具体端（App / H5 / 小程序），未来扩展不需要再改名；
4. 避免 `community_*` 与 `residents` 的语义重叠。

配套命名建议：

| 现名 | 建议名 | 说明 |
| --- | --- | --- |
| `users` | `platform_users` | 平台级 C 端账号 |
| `admin_users` | `admin_accounts` | 后台管理账号（可选，非必须；改了语义更对称） |
| `residents` | `residents` | 保持不变，社区住户档案 |

**第二选择：`platform_accounts`（平台账号）**

它比 `community_users` 合理，但排在 `platform_users` 之后：

- 表内不只登录凭证，还有昵称、头像、信用分、协议留痕、设置等，`users` 更贴合“用户聚合根”；
- 项目已有 `wallet_accounts`（钱包账户），再引入 `platform_accounts` 容易与资金账户混淆；
- 若只改 `users` 而不改 `admin_users`，会出现 `platform_accounts` + `admin_users` 的术语不一致；
- 若团队决定全面采用“账号（account）”术语（`platform_accounts` + `admin_accounts`），它是可接受的统一方案。

次选：

- `user_accounts`：强调“账号”，但表内还有资料、信用、设置，语义略窄；
- `c_end_users`：与代码目录 `api/c_end` 一致，但偏工程术语，对 DBA/运营不够直观；
- `app_users`：容易被理解为仅 App 端，排除 H5/小程序。

若最终不改名，建议至少补数据库注释：

```sql
COMMENT ON TABLE users IS '平台级 C 端账号（移动端/H5/小程序登录身份，可关联 0..n 个社区住户档案）';
```

> 建议：本期不做物理改名；用注释、术语表和只读视图解决可读性问题，把迁移风险留给真正有业务收益的改造。
