# 邻里小栈双端业务闭环评估报告与优化改造方案

> 评估对象：`mobile/`（C 端移动应用）与 `web/`（后台管理端，Vue 3 + FastAPI）
> 评估日期：2026-11-14
> 评估依据：`docs/邻里小栈需求规格说明.md`（下称 SRS）、`mobile/docs/邻家小栈移动端详细设计方案.md`、`web/docs/邻里小栈后台管理系统详细设计说明书.md`，以及两端实际源码与种子数据。
> 结论口径：本报告区分「演示完成度」与「生产/运营就绪度」。前者评价页面、交互与视觉；后者评价双端是否共享业务、数据、状态与资金闭环。

---

## 一、结论摘要

### 1.1 总体结论

**当前 Web 后台无法对移动端真实业务形成运维、运营和管理闭环。**

两端各自是一套完成度较高的「演示系统」：

- 移动端 36 个页面、40 个组件、完整 Mock 全流程，页面与接口契约基本按 SRS/详细设计实现，但 `mobile/config/env.ts` 中 `mock = true`，没有任何真实 C 端服务端；
- Web 端 17 个 Vue 页面、27 张数据表、81 个管理端接口，登录、RBAC、CRUD、MinIO 预签名等可运行，但管理的是**另一套 Fixture 数据**（社区、用户、物品、订单、纠纷与移动端 Mock 均不一致）；
- 两端没有共享数据库、共享实体 ID、共享状态机、共享接口或事件；移动端约 100+ 个 C 端接口在 Web 后端**一个都不存在**，Web 后端 81 个管理端接口移动端**一个都不调用**；
- SRS 中 P0 的实名/业主认证、AI 质检人工复核、担保支付托管、退款/强制放款、双人复核、举报处理、信用体系、通知投递、数据范围隔离等关键能力，后台尚未实现或仅有演示字段。

因此，当前形态适合**立项汇报、视觉评审、交互走查**，不适合试点运营，更不能承载真实资金与用户隐私。

### 1.2 评分（生产/运营就绪度）

| 维度 | 权重 | 得分 | 判断 |
| --- | :-: | :-: | --- |
| 业务闭环（C 端业务能否被后台真实管理） | 25 | 3 | 两端数据与实体完全脱节 |
| 功能完整性（对照 SRS W01–W08） | 20 | 8 | 页面框架齐全，核心审核/资金/治理缺失 |
| 数据模型与契约一致性 | 15 | 3 | 无共享用户/订单/物品实体，枚举与 Fixture 不一致 |
| 资金与交易正确性 | 15 | 3 | 无账本、无余额、无退款/放款/双人复核 |
| 安全合规与审计 | 10 | 2 | 后端未强制权限/数据范围，审计日志不落库 |
| 运营效率与易用性 | 8 | 4 | 页面可用，但大量静态指标与假交互 |
| 工程质量与可运维性 | 7 | 2 | 仅 1 个健康检查测试，无迁移、无幂等、无 CI |
| **合计** | **100** | **25** | **演示级，非运营级** |

> 若只评「视觉与交互演示完成度」，移动端约 90 分、Web 端约 85 分；但本报告评的是双端业务闭环与生产就绪度，因此为 25 分。

### 1.3 十个最关键的断点

1. **没有统一服务端**：移动端全部走 Mock；Web 后端只服务后台自己，不存在 SRS 要求的「两端共用服务端 API」。
2. **没有共享实体**：Web 的 `items/orders/disputes/platform_users` 与移动端 `Item/Order/SellerSummary/UserProfile` 没有 `user_id`、`item_id` 级关联，只有同名字符串。
3. **Fixture 互不相干**：移动端当前小区是「阳光花园小区（c1）」，Web 种子默认小区是「云栖里社区（id=1）」；移动端用户是 `u1/邻居小林`，Web 用户是「林嘉禾/夏木」等，无法互查。
4. **状态枚举不一致**：移动端物品状态为 `DRAFT/AUDITING/ON_SALE/RESERVED/OFF_SHELF/REJECTED/SOLD`，Web 用中文「待审核/在售/已下架」；订单状态移动端为 `PENDING_PAYMENT/ESCROWED/...`，Web 为「已完成/托管中」等自由文本。
5. **AI 质检链路缺失**：Web 只有「审核通过/下架」两个动作，没有 `item_audits`、AI 维度得分、风险标签、置信度、驳回建议、人工复核队列与快车道阈值（SRS W03-01/A-01~A-10）。
6. **资金链路是演示**：没有用户钱包、托管账本、余额、放款/退款/强制划扣、双人复核、回调验签、真实对账；提现审核为单人一步到位（SRS W06/NF-13/AC-08）。
7. **订单只读、纠纷不闭环**：后台订单页只能查询；纠纷「冻结资金」只是往陈述文本追加一行，不改变订单、托管或钱包任何状态。
8. **权限与审计未落地**：`require_permission()`、`allowed_community_ids()` 已定义但**没有任何路由调用**；`AuditLog` 仅在种子数据中写入 3 条，真实操作不产生审计；写接口无幂等、无乐观锁。
9. **运营配置不生效**：公告/通知任务没有投递记录与阅读统计；参数「发布」是空操作，未绑定移动端 `AppConfig`；类目、热词、运营位、邻近半径均无管理入口或未联通。
10. **大量静态假交互**：运营指标、资金结构、图表、分页、批量操作大量硬编码或仅弹 Toast；报表导出接口固定返回空列表；页面静态扫描有 47 行「已准备就绪/已打开/showToast」占位交互。

## 二、评估范围与方法

### 2.1 评估范围

| 范围 | 内容 |
| --- | --- |
| 移动端 | 36 个页面（`mobile/pages/`）、40 个组件、9 个 Pinia Store、15 个 API 模块、14 个 Service、Mock 数据与路由 |
| Web 后端 | 27 张表、11 个 API 路由模块、81 个接口、认证/会话/CSRF/MinIO/种子数据 |
| Web 前端 | 17 个页面、6 组导航、路由守卫、权限码控制、Axios 封装、AppShell |
| 上游文档 | SRS 全部功能/业务规则/验收标准；两端详细设计说明书；移动端接口契约 |
| 不在范围 | 视觉像素级还原、性能压测实测、第三方服务真实联调（均未具备条件） |

### 2.2 评估方法

1. **代码事实核对**：逐模块阅读页面、模型、接口、Store、Service、Mock、数据库模型与种子数据；
2. **业务闭环推演**：以「移动端发起 → 服务端落库 → 后台可见/可审 → 结果回传移动端」为标准链路，逐业务域推演；
3. **需求覆盖对标**：以 SRS M01–M07、W01–W08、BR-01–BR-14、AC-01–AC-10 为检查表；
4. **实现真实性审计**：区分「真实落库」「只读/演示数据」「仅 Toast/静态」「完全缺失」四类；
5. **风险分级**：按资金、合规、用户信任、运营效率、工程质量五个维度评 P0/P1/P2。

### 3.2 核心业务对象与状态机（移动端已建模）

**物品 Item**（`mobile/models/item.model.ts`）

```
DRAFT → AUDITING → ON_SALE → RESERVED → SOLD
                    ↘ REJECTED（可改后重提）      ↘ OFF_SHELF
```

- 三种交易方式：`MONETARY`（货币担保）、`FREE_GIFT`（免费赠与）、`BARTER`（互换，必须填写期望交换描述）；
- 发布约束：本小区强绑定、至少 3 张照片、AI 质检通过后才可上架、30 天有效期。

**订单 Order**（`mobile/models/order.model.ts`）

```
PENDING_PAYMENT → ESCROWED → APPOINTMENT → INSPECTING → COMPLETED
        ↘ CANCELLED        ↘ REFUNDED        ↘ DISPUTING
APPLIED → PENDING_CONFIRM → CONFIRMED → COMPLETED（赠与/互换）
```

- 页面动作位已按状态提供：`canPay/canConfirmApplication/canCompleteTrade/canAppointment/canInspect/canReview/canCancel/canDispute`；
- 货币订单有托管与放款语义，赠与/互换为申请-确认-交割语义；三者在 UI 上已区分。

**认证 AuthStatus**（`mobile/models/user.model.ts`）

```
NOT_LOGIN → LOGGED_IN_UNVERIFIED → VERIFYING → VERIFIED_UNOWNER
                                  ↘ REJECTED
VERIFIED_UNOWNER → SUBMITTING_PROOF → PENDING_AUDIT → VERIFIED_OWNER
                                                     ↘ REJECTED
VERIFIED_OWNER ⇄ FROZEN
```

**其他状态**：AI 质检 `PROCESSING/PASSED/REJECTED/TIMEOUT`；提现「申请 → 风控/人工 → 打款中 → 到账/失败」；纠纷「提交 → 调解 → 解决」；好友申请 `PENDING/ACCEPTED/REJECTED`。

### 3.3 移动端对后台的刚性依赖

移动端不是「纯前端展示」，它已经定义了完整的服务端契约，下列能力必须由后台/平台服务端提供，否则移动端只能停留在 Mock：

| 业务域 | 移动端已有调用 | 后台必须提供 |
| --- | --- | --- |
| 认证/小区 | 登录、实名、业主证明、小区绑定/搜索 | 认证审核队列、材料私密存储、驳回原因、冻结/撤销、强制绑小区 |
| 物品/质检 | 发布、提交质检、进度轮询、报告、上下架/续期 | AI 质检编排、报告持久化、人工复核、禁售库、举报下架 |
| 交易/订单 | 三种订单、预约、验货、取消、纠纷、评价 | 订单状态机、超时任务、双方确认、评价与信用、纠纷证据 |
| 资金 | 预支付、状态轮询、钱包、提现 | 支付网关、托管账本、放款/退款、钱包余额、提现双复核、对账 |
| 内容/社交 | 留言、私信、好友、生活/喇叭/互助 | 内容安全审核、举报处理、会话取证、通知投递 |
| 通知 | 通知中心、未读数、设置、WebSocket | 站内信/推送/短信模板与投递记录、已读回执 |
| 配置 | 类目、AppConfig、热词、头像库 | 类目/参数/运营位管理，且真实下发 |

> 事实依据：`mobile/api/*.api.ts` 共定义约 100+ 个 C 端接口；`web/backend/src/api/*.py` 共 81 个管理端接口，路径前缀为 `/api/v1/admin`，与移动端 `/v1` 契约**无交集**。

### 4.2 数据模型审计

Web 后端现有 27 张表，**缺失 SRS 9.1 与后台详细设计 6.3 中的全部 C 端核心实体**：

## 七、总体判断

### 7.1 做得好的部分

1. **移动端页面与交互覆盖度高**：36 页覆盖 SRS M01–M07 主路径，三种交易方式、AI 质检、认证、IM、钱包均有页面与状态模型；
2. **接口契约意识强**：`api/*.api.ts` 与 `models/*` 已按统一响应、分页、幂等键、错误码设计，切换到真实后端成本可控；
3. **设计系统完整**：Token、40 个组件、多状态 SVG、深浅色预留，视觉一致性好；
4. **Web 端框架与视觉完成度高**：登录、RBAC、CRUD、MinIO、CSRF、统一响应已跑通，具备继续演进的基础；
5. **设计文档质量高**：后台详细设计已给出领域模型、状态机、权限、幂等、Outbox、表结构，改造不需要从零设计。

### 7.2 核心判断

> **移动端是「真前端 + 假后端」，Web 端是「真后台 + 假业务」。**
>
> 两者都完成了「像」，但都没有完成「通」。当前后台对移动端业务的管理能力，仅限于**在另一套样例数据上演示管理动作**，不具备真实运维、运营与管理价值。

### 7.3 改造的有利条件

- 业务规则、状态机、表结构、接口契约都已在文档中定义，**改造主要是「按设计补齐实现」，不是重新做产品设计**；
- 移动端网络层与模型已抽象，接入真实网关主要是切换 `mock`、对齐枚举与补端能力；
- Web 端已有可复用的外壳、权限码、CRUD 模板与 MinIO；
- 当前无生产数据，**可以按目标模型重建数据库，迁移成本低**。

## 八、优化、升级与改造方案

### 8.1 目标与原则

**目标**：用 16 周左右，把双端从「各自演示」升级为「同一平台、同一数据、同一状态机」的可试点运营系统。

**六条原则**：

1. **一个平台、一套数据**：C 端与后台共用服务端、数据库、领域模型与事件；后台不是第二套业务系统。
2. **状态机唯一**：物品、订单、提现、纠纷、认证的状态与迁移只在服务端定义，两端只做展示与触发。
3. **资金先于功能**：先做托管账本、幂等、双人复核、审计，再做运营功能。
4. **权限与审计默认开启**：所有管理端接口默认鉴权、默认数据范围、默认留痕。
5. **以 SRS 验收标准为 Definition of Done**：AC-01–AC-10 作为阶段出口，不以页面数量衡量进度。
6. **Mock 只用于开发**：staging/prod 禁止 `mock=true`；演示数据与生产数据物理隔离。

### 8.3 领域模型与数据底座

按后台详细设计 6.3 落地，优先补齐以下表（字段以设计文档为准）：

| 域 | 表 | 关键关系/说明 |
| --- | --- | --- |
| 身份与社区 | `users`、`certifications`、`residents`、`communities`、`user_penalties` | `users.id` 为全平台用户主键；`residents.user_id + community_id` 唯一；`certifications.user_id/resident_id` 关联审核单 |
| 物品与质检 | `items`、`item_media`、`item_audits`、`item_categories` | `items.seller_id → users.id`；`item_media` 存对象键；`item_audits` 存 AI 维度/置信度/决策/复核人 |
| 交易 | `orders`、`order_items`、`appointments`、`order_events` | 订单关联 `buyer_id/seller_id/item_id`；互换存物品快照；`order_events` 为时间轴与双方确认记录 |
| 资金 | `payment_transactions`、`wallet_accounts`、`ledger_entries`、`withdrawals`、`finance_adjustments`、`reconciliations` | 复式记账：用户余额、托管、平台收入、渠道清算；提现 `reviewer_id/reviewer2_id` |
| 内容与社交 | `life_posts`、`broadcasts`、`help_requests`、`help_responses`、`item_comments`、`conversations`、`messages`、`reviews`、`reports` | 所有 UGC 带 `author_id/status`；举报关联对象与处理人 |
| 信用 | `credit_logs`、`credit_rules` | 交易/评价/违规事件产生流水，分数可重算 |
| 通知 | `notices`、`notice_reads`、`notification_templates`、`notification_tasks`、`notification_records` | 站内信/推送/短信统一投递记录与已读 |
| 治理 | `disputes`、`dispute_evidences`、`dispute_messages`、`repair_orders`、`feedbacks` | 证据存私有桶；调解沟通留痕 |
| 系统 | `admin_users`、`roles`、`permissions`、`audit_logs`、`idempotency_keys`、`outbox_events`、`export_jobs`、`parameter_keys/items`、`dictionaries` | 权限/审计/幂等/事件/导出 |

**建模硬约束**：

- 禁止用姓名/昵称作为业务外键；全部使用 `*_id`；
- 金额统一 `*_cents BIGINT`，禁止浮点；
- 所有核心表带 `version` 并启用 SQLAlchemy `version_id_col`；
- 所有写操作带 `X-Idempotency-Key`；
- 所有状态变更通过服务端状态机，禁止直接 `UPDATE status`；
- 敏感字段（身份证号、姓名、手机号、提现账户）加密存储 + 哈希索引 + 脱敏展示。

### 8.4 关键流程闭环设计

#### 8.4.1 认证闭环

```text
移动端提交实名/业主证明
  → 上传私密桶（预签名 PUT + 上传确认）
  → 创建 certifications 审核单（PENDING）
  → 后台审核队列（材料查看/OCR/人脸结论/小区比对）
  → 通过：users 认证状态 + residents 绑定小区
  → 驳回：必填原因 ≥10 字 + 通知（站内信/短信）
  → 冻结/撤销：自动下架该用户全部在售物品 + 审计
```

验收对应：AC-01、AC-03、AC-08。

#### 8.4.2 发布与 AI 质检闭环

```text
创建物品 DRAFT（校验本小区、类目、3–12 张照片）
  → 提交 AUDITING（幂等）
  → AI 质检 Worker（图像质量→图文一致→合规→汇总）
  → 写入 item_audits（维度/置信度/风险/建议/trace_id）
  → PASS：进入人工复核队列（高置信度可快车道）
  → NEED_HUMAN：人工复核
  → FAIL：REJECTED + 驳回原因/建议 + 通知
  → 复核通过：ON_SALE（30 天过期任务）
  → 任一环节下架/违规：OFF_SHELF + 审计 + 通知
```

验收对应：AC-02、AC-03、W03-01、A-01~A-10。

#### 8.4.3 订单与担保支付闭环

```text
货币交易：
创建订单（锁定物品 RESERVED）
  → 创建支付意图（幂等）→ 渠道支付
  → 回调验签 → 记 ledger：买家余额/渠道 → 托管
  → ESCROWED → 预约 → 验货
  → 双方确认成交 → 放款 ledger：托管 → 卖家钱包（扣平台服务费）
  → COMPLETED → 互评 → 信用流水
  → 任一方不满意 → REFUNDED（原路退回）
  → 超时未付/未确认 → 定时任务取消/自动放款
赠与/互换：
APPLIED → 卖家确认 → 预约 → 双方确认交割 → COMPLETED
```

验收对应：AC-05、AC-06、BR-08、BR-11~BR-13。

#### 8.4.4 提现闭环

```text
用户申请 → 校验余额/限额/频次 → 风控
  → 待审核 → 初审（reviewer_id）
  → 大额/风险命中 → 复审（reviewer2_id，不得同一人）
  → 打款中 → 渠道回调 → 已到账
  → 失败 → 重试/关闭（不得改金额/账户）
  → 全程 ledger + 审计 + 通知
```

验收对应：W06-03/04、NF-13、AC-08。

#### 8.4.5 纠纷闭环

```text
用户提交纠纷（陈述 + ≤9 张证据）
  → disputes + dispute_evidences + 订单 DISPUTING + 冻结托管
  → 后台查看证据/双方陈述/沟通记录
  → 调解记录（dispute_messages）
  → 结论：继续履约/取消/退款/强制放款/部分退款/信用处理
  → 资金类结论 → finance_adjustments 双人复核 → 执行
  → 订单关闭 → 通知双方 → 信用流水 → 审计
```

验收对应：W05-02、AC-08。

#### 8.4.6 通知闭环

```text
领域事件（审核通过/订单状态/提现/纠纷）
  → Outbox → RabbitMQ
  → 通知消费者（模板渲染、去重、频控）
  → 站内信记录 + Push/短信
  → 移动端通知中心/未读数/已读回执
  → 后台查看投递明细/失败重试
```

### 8.8 安全合规专项（P0）

1. **权限**：所有管理端路由挂 `require_permission`；仓储层强制 `data_scope`；跨社区访问拒绝并审计；CI 增加越权用例。
2. **2FA**：TOTP 绑定/验证/恢复码；敏感操作二次验证；登录失败锁定与验证码。
3. **审计**：统一中间件记录操作人、动作、对象、前后快照、IP、UA、traceId；审计日志只追加，不可改删；导出审计。
4. **资金**：复式记账、托管与自有资金隔离、支付回调验签、幂等、双人复核、日终对账、差异告警；禁止任何「直接改余额」接口。
5. **隐私**：身份证/姓名/手机号/提现账户 AES-256-GCM 加密；哈希索引查重；默认脱敏；明文访问单独授权并审计；私有桶短时效签名；注销匿名化。
6. **内容**：UGC 全量内容安全（文本+图片）；举报必达；违规下架/处置留痕；IM 敏感词与外链提醒。
7. **基础设施**：HTTPS、CSP/安全头、限流、上传类型/内容校验、病毒扫描、依赖扫描、备份（RPO ≤5min/RTO ≤1h）。

### 8.11 风险与对策（执行层）

### 8.12 组织与治理

- **双周迭代**，每迭代以「可验收的业务闭环」为交付，不以页面数计；
- **领域 Owner**：身份/交易/资金/内容/系统各 1 人，负责模型与状态机；
- **变更评审**：涉及资金、认证、隐私、审核的 PR 必须双人评审 + 安全清单；
- **Definition of Done**：接口有鉴权/审计/幂等/测试；前端有加载/空/错/权限态；文档与 OpenAPI 同步；
- **度量**：每周跟踪 AC 通过数、P0 缺陷、接口 P95、AI 误杀率、对账差异。

### 8.14 两周 Quick Wins（不改架构，先止血）

1. **后端强制鉴权**：给所有管理端路由加 `require_permission`，仓储加 `data_scope`；越权立即返回 403。
2. **审计中间件**：统一记录写操作前后快照、操作人、IP、traceId。
3. **幂等中间件**：Redis + `idempotency_keys` 表，先覆盖审核/提现/纠纷/参数。
4. **去掉假数据**：工作台/运营指标改为 SQL 聚合；分页改真分页；批量操作与导出未实现则隐藏或标注「未开放」。
5. **enum/契约统一**：输出一份状态字典，两端共用；生成 OpenAPI 与 TS 类型。
6. **认证审核页**：用现有 `Resident` + MinIO 预签名，先做「材料查看 + 通过/驳回原因」。
7. **通知先通站内信**：`notification_records` + 移动端通知中心，先不接 Push/短信。
8. **参数绑定**：把 `AppConfig` 的 8 个参数接到 `parameter_items`，保存即生效（先读缓存）。

### 9.2 评估口径说明

- 「已实现」指接口真实落库且页面可操作；「部分」指有表/接口但缺关键环节或与移动端脱节；「演示」指只改状态/静态数据/Toast；「缺失」指无表、无接口、无页面。
- 覆盖度为**功能点覆盖**，不代表质量；同一功能可能「有页面但不可用」。
- 本报告不评价 Figma 像素还原细节，视觉问题另见两端详细设计的 R-01 等风险项。

**最终结论**：当前系统可作为高质量的交互原型和需求载体，但不能作为生产后台。改造的关键不是继续加页面，而是**先建立统一服务端与共享领域模型，再按 SRS 的资金、认证、审核、治理顺序逐域闭环**。在 16 周、约 100 人周的投入下，双端可以从「各自演示」升级为「可试点运营」的平台。
