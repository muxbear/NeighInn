## 1. 引言

### 1.1 编写目的

本文档定义"邻里小栈（Neighbor's Inn）"平台的产品定位、业务范围、功能需求与非功能需求，作为产品、设计、开发、测试各方开展工作的依据，并作为后续需求变更管理与验收的基线。

预期读者：产品经理、架构师、前后端开发工程师、UI/UX 设计师、测试工程师、运营人员及项目管理者。

### 1.2 项目背景与痛点

邻里小栈是面向**同一小区及相邻小区住户**的闲置物品共享交易平台。产品旨在解决以下痛点：

| 编号 | 痛点 | 平台对应方案 |
| --- | --- | --- |
| P1 | 住户家中存在大量闲置且有价值的物品（如婴儿床、儿童玩具、小家电等），丢弃可惜，且具有很高的二次利用价值 | 提供小区内闲置物品发布与流转渠道，让闲置物品重新进入使用循环 |
| P2 | 线上购物费用高、物流周期长（快则 1~2 天，慢则 3~4 天甚至更久），收货不满意时退换货流程繁琐 | 同小区就近交易，**当日可达**；支持线下验货、当面确认，满意再成交，天然消除"货不对板"与退换货问题 |
| P3 | 闲置物品变卖既可节省家庭空间，又能带来二次收益 | 提供便捷的上架工具与安全收款通道，降低变卖门槛 |
| P4 | 解决"购物最后一公里"问题 | 物品以**本小区商店**为主，业主线上浏览、线下验货交易，步行即达 |
| P5 | 跨小区浏览时无法判断物品的实际远近 | 系统基于地图能力，明确给出物品与业主的**精确距离及步行/骑行/驾车耗时** |
| P6 | 二手交易普遍存在描述不清、信息不对称、货不对板 | 强制要求**全方位照片**、完整程度与质量说明，可选上传视频、发票等凭证 |
| P7 | 二手平台上劣质品、违规品泛滥，人工审核成本高 | 引入 **AI 大模型与智能体技术**对上架物品进行分析、检测与质量评估，不达标物品禁止上架 |
| P8 | 陌生人交易缺乏信任基础 | 发布者必须**实名认证**并提供**本小区业主证明**，交易双方均为可信的邻里身份 |

### 1.3 产品定位

> **一句话定位**：基于真实小区邻里关系的、AI 质检护航的、以线下验货交易为主的闲置物品共享平台。

核心特征：

- **可信**：实名认证 + 业主证明 + AI 质检，三重保障；
- **就近**：以本小区商店为核心，辐射邻近小区，分钟级可达；
- **透明**：距离与通勤耗时可视化，全方位物品影像资料，所见即所得；
- **灵活**：免费赠与、物品互换、担保货币交易三种流转方式，适配不同场景；
- **高效**：线上撮合、线下验货、当面交割，砍掉物流与退换货环节。

### 1.4 范围

**本期范围（v1.1）**：

- 移动端（面向 C 端小区业主）：注册与实名认证、小区绑定、闲置物品发布（含 AI 质检）、浏览与搜索、即时沟通、**三种交易方式（免费赠与 / 物品互换 / 货币交易·平台担保支付）**、线下验货交割确认、评价与信用；
- **社交体系**：物品留言、私信、好友关系（互加好友后可自由互发消息）；
- Web 端（面向平台运营与管理）：业主资质审核、小区管理、商品复审、AI 审核结果人工复核、订单与纠纷处理、**资金与担保支付管理**、数据看板、运营配置；
- AI 能力：物品图像质量评估、合规性检测、商品信息辅助生成；
- 基础支撑：地图与距离耗时服务、对象存储、消息通知、内容安全、支付与资金托管服务。

**本期范围之外**（列入演进规划，见第 13 章）：求购发布、社区公益捐赠、积分商城、开放 API 等。

### 1.5 术语与缩略语

| 术语 | 定义 |
| --- | --- |

## 2. 总体描述

### 2.1 产品愿景

让每一个小区的闲置物品在邻里之间高效、可信地流转起来，构建"**15 分钟生活圈**"内的绿色共享消费生态。

### 2.2 运行环境

| 端 | 环境 |
| --- | --- |
| 移动端 | 微信小程序（首选）/ Android App / iOS App，适配主流机型，最低支持 Android 8.0 / iOS 13 |
| Web 端 | 主流桌面浏览器（Chrome / Edge / Firefox / Safari 近两年主版本），推荐分辨率 1920×1080 |
| 服务端 | 云部署（容器化），依赖：关系型数据库、缓存、对象存储、消息队列、地图服务、AI 大模型服务 |

### 2.3 用户群体画像

| 用户群 | 特征 | 核心诉求 |
| --- | --- | --- |
| 卖家业主 | 家中有闲置物品的住户 | 快速上架、安全变现、节省空间 |
| 买家业主 | 有就近购物需求的住户 | 就近、低价、可信、即买即得 |
| 平台运营 | Web 端管理与服务人员 | 高效审核、纠纷处理、数据洞察 |
| 系统管理员 | Web 端超级管理员 | 账号权限、系统配置、安全管控 |

### 2.4 核心价值假设

- 小区半径内（< 3 km）的交易，信任成本与履约成本远低于全网二手平台；
- "线下验货、当面交割"模式可将纠纷率与退货率降低一个数量级；
- AI 质检前置拦截可显著降低人工审核成本，并提升平台上架物品的整体质量水位。

## 4. 业务流程

### 4.1 总体业务流程

```
业主注册 → 实名认证（选做，可跳过）/ 提交住户认证（业主证明）→ 平台审核 → 绑定本小区
    （实名与住户认证相互独立；实名审核不阻塞住户认证提交与审批）
    │
    ├─【卖家】发布物品（全方位照片 + 完整程度 + 质量说明 + 可选视频/发票）
    │        → 选择交易方式：① 货币交易（担保支付）② 免费赠与 ③ 物品互换（描述期望交换的物品）
    │        → AI 质检（不达标→驳回并给出改进建议；达标→进入人工复核队列）
    │        → 人工复核通过 → 上架至本小区商店
    │
    ├─【买家】浏览本小区/邻近小区物品（含距离与步行/骑行/驾车耗时）
    │        → 收藏 / 留言 / 私信卖家 / 加好友
    │        → 按交易方式发起：
    │            ① 货币交易：在线支付货款至平台托管 → 预约线下验货
    │            ② 免费赠与：申请领取 → 卖家确认 → 预约线下交割
    │            ③ 物品互换：提交自己的交换物品 → 卖家同意 → 预约线下交割
    │        → 线下当面验货 → 双方满意确认 → 平台放款（货币交易）/ 交割完成（赠与/互换）
    │        → 互评 → 信用累积
    │
    └─【异常】验货不满意 → 拒收并原路退款（货币交易）/ 取消（赠与/互换）
              纠纷 → 平台介入调解（可冻结资金、物品、账号）
```

### 4.2 关键业务规则

| 编号 | 规则 |
| --- | --- |
| BR-01 | 一个自然人账号只能实名认证一次；认证信息不可自行修改，需走申诉流程 |
| BR-02 | 业主**只能将物品发布到本小区商店**，系统按业主证明认定的小区强绑定 |
| BR-03 | 邻近小区物品默认对业主可见，阈值（距离/小区数）由运营在 Web 端配置 |
| BR-04 | 未通过 AI 质检的物品**不得进入人工复核与上架流程**，需修改后重新提交 |
| BR-05 | 物品至少上传 3 张多角度照片（含整体、细节、缺陷处），最多 12 张；视频与发票为可选凭证 |
| BR-06 | 物品支持三种交易方式（卖家发布时选择其一）：**① 货币交易（担保支付）**、**② 免费赠与**、**③ 物品互换**。所有方式均默认以"线下验货 + 当面交割"履约，双方在移动端确认后订单闭环 |
| BR-07 | 物品上架有效期为 30 天（可配置），到期自动下架并提醒卖家续期或下架 |
| BR-08 | 同一物品同一时刻只能与一个买家处于"待验货/交易中"订单状态，避免一物多卖冲突 |
| BR-09 | 骑手/搬运等履约服务为增值扩展项，v1.1 不含 |
| BR-10 | 用户注销账号时，其个人信息按《个人信息保护法》要求删除或匿名化，其历史交易记录按法规期限留存脱敏归档 |
| BR-11 | **担保支付规则**：货币交易中，买家须先在线支付货款至平台托管账户，卖家收款前资金不得用于任何用途；买家线下验货确认无误后平台放款给卖家；验货不满意则原路退款；买家签收确认后超时（默认 72h，可配置）未操作，系统自动确认放款 |
| BR-12 | **赠与规则**：赠与物品价格为 0，买家"申请领取"，卖家确认后双方按线下验货流程交割；赠与交易同样计入信用互评；同一卖家每月赠与件数不设上限，但恶意刷赠与行为纳入风控 |
| BR-13 | **互换规则**：卖家发布时可填写"期望交换的物品描述"（结构化标签 + 自由文本）；买家发起互换申请时须提交自己用于交换的物品（可从"我发布的物品"中选择或现场补充说明）；双方均同意后方进入线下验货交割；互换物品均须先通过 AI 质检上架 |
| BR-14 | **社交规则**：任何注册用户可在物品详情页给卖家留言（公开，留言需过内容安全审核）；用户之间可申请加好友，对方同意后成为好友并可随时互发私信（不依赖具体物品）；好友与私信功能仅限已实名用户；好友数量上限默认 500（可配置）；用户可删除好友、拉黑或举报对方 |

### 4.3 状态机定义

**物品状态机**：`草稿 → 待AI质检 → AI驳回(终态/可改) → 待人工复核 → 复核驳回(可改) → 已上架 → 已预约 → 交易中 → 已售出(货币交易/互换完成) / 已赠出(赠与) → 已下架/违规下架(终态)`

**订单状态机（货币交易·担保支付）**：
`已创建(待付款) → 待验货(已托管) → 验货中 → 已成交·待放款 → 已完成(放款成功,互评后闭环)`
`已创建(待付款) → 已取消(超时未付,默认30分钟)；验货不满意 → 退款中 → 已退款(关闭)；任意非终态 → 纠纷中 → 已调解(放款/退款后关闭)`

**订单状态机（赠与/互换）**：
`已申请/已发起 → 待对方确认 → 待验货 → 验货中 → 已完成(双方确认交割,互评后闭环)；任意非终态 → 已取消 / 纠纷中 → 已调解(关闭)`

**认证状态机**：`未认证 → 待审核 → 已认证 / 已驳回(可重新提交)；已认证 → 冻结(违规)`

**好友关系状态机**：`无 → 好友申请中 → 已好友(可互发私信)；已好友 → 已删除 / 已拉黑`

## 5. 功能需求 — 移动端（C 端业主）

> 优先级定义：**P0** = 首版必须；**P1** = 首版应具备；**P2** = 后续迭代。
> 需求编号规则：`M-模块-序号`。

### 5.1 账号与认证（M01）

| 编号 | 需求 | 优先级 | 说明 |
| --- | --- | :-: | --- |

## 7. AI 智能能力需求

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| A-01 | **物品图像质量评估**：对上传照片逐张评估清晰度（模糊检测）、曝光（过暗/过曝）、遮挡与完整性，输出每张照片得分；整体照片集需覆盖"整体照 + 细节照"，不满足 BR-05 结构要求时驳回 | 置信度低于阈值的转入人工复核而非直接驳回，避免误杀 |

### 8.2 距离与耗时计算规格（对应痛点 5）

1. **数据基础**：小区在 Web 端通过地图选点录入精确坐标（精度不低于门址级，误差 ≤ 50m）；业主坐标取其绑定小区坐标；物品坐标取其所属小区坐标。
2. **直线距离展示**：列表卡片展示球面直线距离（保留到 10m 级），前缀"约"。
3. **耗时预估**：详情页与卡片调用地图服务路径规划 API，分别按**步行（默认 4.8km/h）**、**骑行（默认 12km/h，取实时/历史路况修正）**、**驾车（含实时路况）**三种模式返回预估耗时，展示为"步行约 12 分钟 / 骑行约 4 分钟 / 驾车约 3 分钟"。
4. **降级策略**：地图服务不可用时，按直线距离与默认速度本地估算并标注"预估"。
5. **缓存**：同源-目标小区对 + 出行方式的耗时结果缓存 ≥ 6 小时（驾车路况缓存 ≤ 15 分钟），控制调用量。

### 8.3 接口通用约定

- 服务端 RESTful API（JSON），移动端与 Web 端统一走网关；
- 认证：移动端 Token（JWT），Web 端会话 + 双因素；敏感接口二次校验；
- 幂等：订单、发布等写操作支持幂等键；分页、排序、错误码规范统一（附录 14.3）。

## 11. 约束与假设

### 11.1 约束

1. 担保支付必须对接**持牌支付机构**（微信支付/支付宝/银联等），托管资金与平台自有资金隔离存管，平台不得自建资金池；提现、强制放款/退款等资金操作须双人复核并全量留痕（见 BR-11、NF-13）；
2. 发布范围严格限定本小区，跨小区交易开关默认关闭，开启需运营决策（涉及邻近小区信任边界）；
3. AI 质检为**上架必要非充分条件**：AI 通过后仍需人工复核（高置信度快车道除外），最终上架决定权在平台；
4. 业主身份认定以平台审核通过的证明材料为准，平台不对业主物权做法律背书，需在用户协议中明确免责条款；互换、赠与交易的物权风险由交易双方自行承担，平台提供留痕与调解；
5. 地图服务、实名认证服务与支付渠道依赖第三方可用性与收费策略。

### 11.2 假设

1. 目标用户具备智能手机并习惯扫码/小程序操作；
2. 物业配合提供小区坐标与常用交易地点信息（初期可人工录入）；
3. 前期以单城市试点运营，按小区逐个开通，跑通模式后再复制。

## 12. 验收标准

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-01 | 注册→实名→业主认证→绑定小区全流程走通 | 全流程无阻断，驳回原因可读，审核结果通知到位 |
| AC-02 | 发布流程与 AI 质检 | 上传 3+ 张照片完整走通；故意提交模糊照片/图文不符/禁售品时，AI 正确拦截并给出改进建议；达标物品可在人工复核后上架 |
| AC-03 | 发布范围限定 | 任一已认证业主无法将物品发布到非绑定小区（服务端强校验） |
| AC-04 | 距离与耗时展示 | 物品卡片与详情页正确展示与业主的距离及步行/骑行/驾车三种耗时，误差在地图服务允许范围内；地图服务中断时降级为估算并标注 |
| AC-05 | 预约验货交易闭环 | 预约→改期/取消→双方确认成交/未成交→互评全状态机流转正确；一物多卖冲突被 BR-08 规则阻止 |
| AC-06 | 三种交易方式 | ① 货币交易：支付→托管→验货→确认放款→提现全链路走通，验货不满意可原路退款，超时未付自动取消、买家超时未确认自动放款；② 赠与：申请领取→卖家确认→交割闭环；③ 互换：发起互换（含期望交换描述）→双方确认→交割闭环；三种方式均正确计入信用互评与统计报表 |
| AC-07 | 留言、私信与好友 | 物品留言公开可见且过内容审核；好友申请/同意/删除/拉黑流转正确；好友间可互发私信且不依赖物品；敏感词与风控提醒生效 |
| AC-08 | Web 端审核与运营 | 资质审核、商品复核、纠纷调解、资金流水查询、参数配置均可用且留痕；RBAC 权限隔离有效；强制放款/退款需双人复核 |
| AC-09 | 非功能指标 | NF-01/NF-05 压测与稳定性测试达标；敏感信息全链路脱敏抽查通过；支付对账无差异 |
| AC-10 | 合规 | 隐私政策、注销通道、内容安全审核、审计日志、资金隔离存管逐项验收 |
