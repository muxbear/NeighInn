## 1. 概述

### 1.1 背景与目标

移动端底部「消息」页目前包含「消息」与「邻居」两个标签页。本期需要把「邻居」标签页从“手动加好友 + 好友列表”升级为“同小区认证住户自动互为邻居好友 + 可直接聊天 + 可拉黑”的完整好友能力。

本方案需要解决五个核心问题：

1. **准入门槛**：只有同时完成“身份认证”和“业务认证”的住户才能使用好友功能。
2. **关系默认值**：同一小区内同时完成两项认证的住户，默认互为好友，不需要逐人申请。
3. **负向关系**：住户可以拉黑好友，拉黑后双方不再出现在彼此的邻居列表中，也不能继续互发消息。
4. **消息能力**：好友之间可以互发文字、表情；图片、视频、声音作为后续能力预留。
5. **技术选型**：调研市场上开源、成熟、稳定的消息服务器与协议，结合本项目现状给出可落地的实现方案。

### 1.2 名词定义

| 术语 | 定义 | 数据口径 |
| --- | --- | --- |
| 身份认证 | 实名认证，证明“这个账号背后是一个真实的人” | `users.realname_status = 'VERIFIED'`，且最新 `certifications.type = 'REALNAME'` 为 `VERIFIED` |
| 业务认证 | 住户认证/业主认证，证明“这个人是本小区真实住户” | `residents` 存在有效记录：`certification_status = 'VERIFIED'`、`status = 'ACTIVE'`、`community_id` 非空；且最新 `certifications.type = 'OWNER_PROOF'` 为 `VERIFIED` |
| 双认证住户 | 同时满足身份认证与业务认证的用户 | 上述两个条件同时成立 |
| 邻居好友 | 同一小区内互为默认好友的双认证住户 | 同 `community_id` + 双方双认证 + 双方账号正常 + 无拉黑关系 |
| 拉黑 | 住户主动阻断与某个邻居的好友关系和消息通道 | `friend_blocks` 中存在 `ACTIVE` 记录 |
| 好友会话 | 不依赖具体物品的 1 对 1 会话 | `conversations.type = 'FRIEND'` |
| 物品会话 | 围绕某个物品产生的 1 对 1 会话 | `conversations.type = 'ITEM'`，保留现有能力 |
| 消息 | 会话中的一条文本、表情或媒体消息 | `messages` 表，按 `conversation_id + seq` 有序 |

### 1.3 本期范围

**本期包含（P0）**

- 双认证准入校验与服务端强制拦截。
- 同小区双认证住户自动成为邻居好友，无需申请。
- 邻居列表：搜索、分页、按楼栋/字母分组、备注名。
- 拉黑、解除拉黑、黑名单管理。
- 好友 1 对 1 会话创建、文字消息、Unicode 表情消息。
- 消息发送幂等、顺序、未读数、已读、断线重连后的消息补偿。
- 内容安全审核、频率限制、举报入口。
- 旧好友申请数据与旧好友关系的兼容迁移。

**本期不包含（P1/P2）**

- 图片、视频、语音消息的实际收发（仅预留消息类型与上传链路）。
- 大表情包/贴纸商店（本期表情 = Unicode 表情，复用文本通道）。
- 群聊、消息撤回、消息转发、消息引用、语音通话、视频通话。
- 跨小区好友、陌生人交友、附近的人。
- 多端消息漫游的完整同步（本期保证同一账号多设备在线推送与基础补偿）。
- 端到端加密（E2EE）。

### 1.4 设计原则

1. **服务端权威**：好友关系、拉黑关系、消息顺序、未读数全部以服务端为准，客户端只做展示与乐观更新。
2. **关系可推导，不物化**：默认邻居关系由“同小区 + 双认证 + 未拉黑”实时推导，避免为每个新住户写入 N 条好友记录。
3. **读写分离的可靠性**：消息先落库再推送；推送失败不影响消息可恢复；客户端按 `seq` 补偿。
4. **最小必要暴露**：邻居列表不展示手机号、详细门牌；楼栋等敏感信息按用户隐私设置展示。
5. **可回滚**：新旧好友体系通过开关切换，迁移脚本可重复执行，旧接口保留一个版本。
6. **先解决契约问题**：当前 WebSocket 帧格式前后端不一致，必须先修复，否则所有实时能力都不可用。

### 1.5 方案摘要

- **关系模型**：不物化好友关系，按“同小区 + 双认证 + 账号正常 + 未拉黑”实时推导邻居列表；移除手动加好友入口，旧申请数据自动迁移。
- **准入校验**：实名认证（REALNAME）+ 住户认证（OWNER_PROOF）同时通过才可使用；服务端统一返回 40304，前端展示认证引导。
- **拉黑**：新增 `friend_blocks`，任一方向拉黑即双向阻断：邻居列表互不可见、好友消息不可发、物品会话只读。
- **消息能力**：本期实现文字 + Unicode 表情（复用 TEXT 通道）；图片/视频/语音预留消息类型与 MinIO 上传链路。
- **技术选型**：不引入 OpenIM/Matrix/XMPP 等重型 IM，采用现有 FastAPI WebSocket + PostgreSQL + Redis Pub/Sub；定义 `clientMsgId` 幂等、会话内 `seq`、服务端 ACK、断线补偿。
- **必须先行修复**：WebSocket 信封统一为 `action/payload`，修复当前服务端 `type/data` 与客户端不一致导致的推送失效问题。

### 2.3 当前必须优先修复的契约问题

**WebSocket 帧格式不一致（P0）**

- 移动端 `ws.service.ts` 使用：

```json
{ "action": "MSG_SEND", "payload": { "clientMsgId": "u1", "conversationId": "c1", "content": "你好" } }
```

- 服务端 `ws.py` 读取 `frame.get("type")` 和 `frame.get("data")`，`ws_manager.push()` 也发送 `{ "type": "MSG_PUSH", "data": ... }`。

结果是：

1. 客户端通过 WebSocket 发送的 `MSG_SEND` 被服务端忽略；
2. 服务端推送的 `MSG_PUSH`、`PONG` 被客户端忽略；
3. 目前实际可用的只有 HTTP 发送消息，实时推送链路实际上未闭环。

**本方案统一采用 `action/payload` 信封**（与移动端现有实现、详细设计 10.3 一致），服务端兼容读取 `type/data` 一个版本，随后移除兼容代码。

## 3. 需求规格与业务规则

### 3.1 角色与前置条件

| 角色 | 前置条件 | 可用能力 |
| --- | --- | --- |
| 未登录用户 | 无有效 Token | 不可访问好友与消息接口 |
| 已登录未实名用户 | `realname_status != VERIFIED` | 不可进入邻居列表、不可发好友消息；可浏览、可走物品交易流程 |
| 已实名未住户认证用户 | 实名通过，但无有效 `Resident` | 不可使用好友功能；提示完成住户认证 |
| 双认证住户 | 实名 + 住户认证均通过，账号正常 | 可查看同小区邻居、聊天、拉黑、举报 |
| 被拉黑用户 | 被某住户拉黑 | 不可向对方发起会话或发消息；邻居列表中不显示对方 |
| 认证被冻结/撤销用户 | `Resident.status != ACTIVE` 或认证状态非 `VERIFIED` | 好友能力自动失效；历史会话转为只读 |

### 3.2 认证判定口径

建议在服务端新增统一判定函数，避免多处重复查询导致口径不一致：

```python
async def get_social_eligibility(db: AsyncSession, user: User) -> SocialEligibility:
    """返回用户是否具备好友功能资格，以及缺失项。"""
    realname_ok = user.realname_status == "VERIFIED" and user.status == "ACTIVE"
    resident = await bound_active_resident(db, user.id)
    owner_ok = bool(
        resident
        and resident.certification_status == "VERIFIED"
        and resident.status == "ACTIVE"
        and resident.community_id
    )
    community = await db.get(Community, resident.community_id) if owner_ok else None
    return SocialEligibility(
        eligible=realname_ok and owner_ok,
        realname_verified=realname_ok,
        owner_verified=owner_ok,
        community_id=resident.community_id if owner_ok else None,
        community_name=community.name if community else "",
        reason_code=(
            "OK" if realname_ok and owner_ok
            else "REALNAME_REQUIRED" if not realname_ok
            else "OWNER_PROOF_REQUIRED"
        ),
    )
```

判定细则：

1. `users.status` 必须为 `ACTIVE`；`FROZEN`、`CANCELLED` 一律不可用。
2. `users.realname_status` 必须为 `VERIFIED`；后台审核通过时已写入，若发现历史数据不一致，以最新 `REALNAME` 认证单为准并做一次修复任务。
3. `residents` 必须存在 `status = 'ACTIVE'` 且 `certification_status = 'VERIFIED'` 的记录。
4. 若一个用户存在多条 `Resident`，以最近一条有效记录为准；建议增加“一个用户仅一条 ACTIVE 住户记录”的约束或数据校验任务。
5. 小区状态必须为 `OPERATING`；小区停用后，该小区住户的好友能力冻结，历史消息只读。
6. 认证撤销、冻结、住户迁出后，下一次请求即失效，不依赖客户端缓存。

### 3.3 默认邻居好友规则

**规则定义**

同一小区内，满足以下全部条件的两个用户互为邻居好友：

```
me 双认证 + 对方双认证
+ 双方 users.status = ACTIVE
+ 双方 residents.community_id 相同且 residents.status = ACTIVE
+ 双方不存在 ACTIVE 的拉黑记录（任一方向）
+ 双方不属于同一用户（自己）
```

**关系特征**

| 特征 | 说明 |
| --- | --- |
| 自动 | 认证通过后自动出现在彼此的邻居列表，无需申请、无需同意 |
| 对称 | A 能看到 B，B 也能看到 A（拉黑除外） |
| 动态 | 新住户认证通过后自动加入；认证撤销/迁出后自动移出 |
| 不物化 | 不预先为每对用户写入好友关系行，查询时实时推导 |
| 不设 500 上限 | SRS 的“好友上限 500”针对手动添加好友；默认邻居关系不应受此限制。若产品坚持上限，只对“特别关注/手动备注”生效 |

**为什么不物化**

假设一个小区有 `N` 个双认证住户：

- 物化方案需要在每次认证通过时写入 `N-1` 条记录，小区 2000 人时单次写入 1999 条；
- 认证撤销、迁出、拉黑都要级联维护；
- 新用户加入后还要回填历史关系；
- 关系本身是可推导的，物化只会带来一致性问题。

因此本期采用“隐式关系 + 拉黑例外表 + 备注表”的方案。

**好友申请如何处理**

- 新体系下不再需要“加好友申请”。邻居列表直接展示所有符合条件的人。
- `friend_requests` 保留用于历史数据与未来跨小区扩展，但前端不再提供新的申请入口。
- 上线迁移时：
  - 对双方都已双认证且同小区的 `PENDING` 申请，自动标记为 `ACCEPTED`，并发送一条站内通知；
  - 对不满足条件的申请，标记为 `REJECTED` 或 `EXPIRED`；
  - 已有 `ACTIVE` 的 `Friend` 行保留作为审计数据，不再参与新关系判定。

**好友数量上限**

- `friend_max_count = 500` 不再限制默认邻居列表。
- 若产品要求控制展示规模，采用“分页 + 搜索 + 按楼栋筛选”，而不是限制关系数量。
- 备注/特别关注可以单独设置上限（例如 500），与默认邻居关系解耦。

### 3.4 拉黑规则

**数据模型**

拉黑是一条有方向的记录（`blocker_id -> blocked_id`），但产品效果按“关系对”处理：只要任一方向存在 `ACTIVE` 拉黑，双方即不再是邻居好友，且不能互发消息。

**产品语义（本期建议）**

| 场景 | 拉黑方（A） | 被拉黑方（B） |
| --- | --- | --- |
| 邻居列表 | 不再显示 B | 不再显示 A |
| 好友会话列表 | 隐藏与 B 的 `FRIEND` 会话 | 隐藏与 A 的 `FRIEND` 会话 |
| 物品会话 | 保留会话，但输入框禁用并提示“你已拉黑对方” | 保留会话，但输入框禁用并提示“对方已将你加入黑名单” |
| 发送消息 | 禁止 | 禁止 |
| 历史消息 | 服务端保留；客户端可“清空聊天记录” | 服务端保留；客户端可“清空聊天记录” |
| 解除拉黑 | 在“设置-黑名单”中解除 | 关系恢复为默认邻居好友（若仍满足双认证同小区） |
| 举报 | 可同时举报 | 可通过物品/会话举报入口举报 |

**约束**

1. 不能拉黑自己。
2. 只能拉黑“当前同小区邻居”或“存在历史会话的用户”，否则返回 404，防止通过接口枚举用户。
3. 重复拉黑幂等：已存在 `ACTIVE` 记录时直接返回成功。
4. 单用户 ACTIVE 拉黑数量上限建议 1000，超过返回 42201。
5. 拉黑/解除拉黑写审计日志（谁、对谁、时间、来源页面）。
6. 拉黑不删除服务端消息；是否允许拉黑方继续查看历史消息由产品决定，本期建议保留只读历史。

**与微信的差异说明**

微信的拉黑偏“单向拒收”，本方案采用“双向阻断 + 双向隐藏”，原因是：

- 小区场景下双方仍可能在线下见面，双向隐藏能降低继续骚扰的概率；
- 实现简单，消息门禁只需判断“任一方向拉黑”；
- 避免“拉黑方还能发消息”造成的产品歧义。

如产品坚持微信式单向语义，需要额外定义“拉黑方是否可发送”“被拉黑方是否可见会话”，本期不建议。

### 3.5 会话与消息规则

| 规则 | 说明 |
| --- | --- |
| 会话类型 | `FRIEND` 好友会话；`ITEM` 物品会话保留现有逻辑 |
| 好友会话创建 | 首次发消息时懒创建；双方任意一方发起都复用同一个会话 |
| 物品会话 | 沿用现有规则：实名用户可围绕物品发起；不受好友双认证限制 |
| 消息类型 | 本期：`TEXT`、`SYSTEM`；表情复用 `TEXT`（Unicode）；预留 `EMOJI`、`IMAGE`、`VIDEO`、`VOICE`、`ITEM` |
| 文本长度 | 1~500 字符（可配置）；空白消息拒绝 |
| 表情 | 本期为 Unicode 表情，随文本发送；纯表情消息允许；后续大表情包使用 `EMOJI` 类型 |
| 消息顺序 | 每个会话内 `seq` 单调递增；客户端按 `seq` 排序 |
| 幂等 | `(conversation_id, sender_id, client_msg_id)` 唯一；重复请求返回同一条消息 |
| 未读 | 以“对方发送且 `seq > 我的已读游标`”的消息数计算 |
| 已读 | 进入会话或滚动到可见区域时上报 `lastSeq`；服务端更新读游标 |
| 撤回/编辑 | 本期不支持；预留 `deleted_at` 与 `RECALLED` 状态 |
| 消息保留 | 默认 3 年（待法务确认）；到期归档或清理 |
| 群聊 | 本期不支持 |

### 3.7 状态机

#### 3.7.1 邻居关系状态

```
不存在
  │ 双方双认证 + 同小区 + 未拉黑
  ▼
邻居好友（隐式，ACTIVE）
  │ A 拉黑 B
  ▼
已拉黑（BLOCKED，任一方向）
  │ A 解除拉黑 + 双方仍满足条件
  ▼
邻居好友（隐式，ACTIVE）

邻居好友
  │ 任一方认证撤销 / 住户迁出 / 账号冻结
  ▼
关系失效（INELIGIBLE，历史会话只读）
```

#### 3.7.2 会话状态

```
不存在
  │ 首次发消息 / 点击邻居
  ▼
ACTIVE（可发送）
  │ 任一方拉黑
  ▼
READ_ONLY_BLOCKED（只读）
  │ 解除拉黑
  ▼
ACTIVE

ACTIVE
  │ 任一方认证失效
  ▼
READ_ONLY_INELIGIBLE（只读）
```

#### 3.7.3 消息状态

```
SENDING（客户端本地）
  │ 服务端落库成功 + ACK
  ▼
SENT
  │ 对方已读
  ▼
READ
  │ 超时/失败
  ▼
FAILED（可重发，仍使用同一 clientMsgId）
```

> 说明：`SENT/READ` 是服务端权威状态；客户端 `SENDING/FAILED` 只存在于本地。

### 3.8 边界与异常

| 场景 | 处理 |
| --- | --- |
| 用户实名通过但住户认证未通过 | 邻居列表返回 40304，`data.reasonCode = OWNER_PROOF_REQUIRED`，前端引导去认证中心 |
| 用户住户认证通过但实名未通过 | 返回 40304，`data.reasonCode = REALNAME_REQUIRED` |
| 双方不同小区 | 不出现在彼此邻居列表；直接调用会话接口返回 40301 |
| 对方认证被撤销 | 邻居列表自动移除；已有会话 `canSend = false`，提示“对方认证状态已变更” |
| 对方账号被冻结/注销 | 同认证撤销；会话只读；不展示对方敏感信息 |
| 用户迁出小区 | 旧小区列表移除；旧会话只读；新小区通过新住户认证后加入新列表 |
| 小区停用 | 该小区所有好友能力冻结；历史消息只读 |
| 重复创建好友会话 | 返回已有会话，不新建 |
| 同一对用户 A→B、B→A 同时创建会话 | 通过 `pair_low_id/pair_high_id` 唯一约束保证只产生一个会话 |
| 拉黑后对方仍尝试发送 | 返回 40305（新增“关系已阻断”错误码），前端显示“消息已发出，但对方拒收”或“你已拉黑对方” |
| 消息重复提交 | `clientMsgId` 幂等，返回同一条消息 |
| 消息乱序到达 | 客户端按 `seq` 排序；缺失 `seq` 时触发补偿拉取 |
| WebSocket 断线 | 指数退避重连；重连后拉取会话列表与当前会话增量消息 |
| 多设备同时在线 | 所有在线设备都收到 `MSG_PUSH`；已读状态以服务端读游标为准 |
| 消息内容命中违禁词 | 42201，不落库；前端提示并保留输入内容 |
| 消息内容命中敏感模式（微信/手机号） | 允许发送，但 `riskFlag` 标记，气泡下方展示风险提示 |
| 发送频率过高 | 42901，前端按钮冷却并提示 |

## 4. 消息服务器与协议选型调研

### 4.1 调研方法与评估维度

调研时间：2026-11-18。评估对象为公开可查的开源即时通信服务器/实时消息服务器及协议。评分按本项目约束进行 1~5 分主观评估：

| 维度 | 说明 |
| --- | --- |
| 功能完整度 | 是否内置单聊、好友/黑名单、离线消息、已读、多端同步 |
| 与现有栈契合度 | 是否容易接入 FastAPI + PostgreSQL + uni-app x，是否要引入新语言/新中间件 |
| 部署运维复杂度 | 依赖组件数量、是否适合中小团队 |
| 许可证友好度 | 是否允许闭源商用/二次开发 |
| 生态与成熟度 | 社区活跃度、文档、SDK、生产案例 |
| 本项目当前必要性 | 当前规模与需求是否真的需要该方案 |

> 说明：以下信息来自各项目官方仓库/文档与公开资料的概要整理，版本、许可证与功能可能随项目演进变化，落地前需以官方最新文档复核。

### 4.3 逐项分析

#### 4.3.1 OpenIM Server

**优势**

- 功能完整：单聊、群聊、离线消息、多端同步、已读、消息类型扩展、推送集成；
- 提供包括 uni-app 在内的多端 SDK，接入形态成熟；
- 微服务架构，支持水平扩展；
- Apache-2.0，商用友好。

**代价**

- 依赖组件多：etcd、MySQL、MongoDB、Redis、Kafka，部署与运维成本显著高于当前项目；
- 用户体系需要与现有 `users/residents/certifications` 打通，存在双写/同步问题；
- 消息存储与现有 `conversations/messages` 表并存，数据治理复杂；
- 当前项目只需要“同小区 1 对 1 文字/表情”，OpenIM 的大部分能力用不上；
- 与现有内容安全、举报、认证撤销联动需要额外开发 Webhook/回调。

**结论**：功能强，但对当前阶段过重。作为规模增长后的演进候选，不作为本期首选。

#### 4.3.2 Matrix Synapse

**优势**

- Matrix 是开放标准，支持联邦、E2EE、VoIP；
- 生态完整，客户端/桥接丰富；
- 适合需要跨组织互联、强隐私的场景。

**代价**

- 联邦、E2EE 对“同小区邻居聊天”没有直接价值；
- Synapse 资源消耗较高，部署与调优复杂；
- AGPL-3.0 对闭源商用有额外约束；
- 需要引入 Matrix 用户 ID、房间模型，与现有用户/小区模型映射成本高。

**结论**：标准完备但过重，不适合本期。

#### 4.3.3 Rocket.Chat

**优势**

- 开源社区成熟，功能全（频道、文件、音视频、集成）；
- 自托管部署方案多；
- MIT 社区版许可友好。

**代价**

- 产品形态是“团队协作聊天”，不是“嵌入现有 App 的 IM 能力”；
- Node.js/Meteor + MongoDB 技术栈与现有 FastAPI/PostgreSQL 不一致；
- UI/权限模型偏企业团队，改造成本高；
- 移动端集成需要大量二次开发。

**结论**：不适合作为嵌入式好友聊天底座。

#### 4.3.4 Mattermost

**优势**

- Go 编写，性能好，部署相对简单；
- Slack 替代品，频道/文件/搜索/集成完善；
- 社区活跃。

**代价**

- 同样是团队协作产品，不是 IM PaaS；
- 用户/频道/权限模型与小区邻居关系不匹配；
- 移动端 SDK 与现有 uni-app x 集成成本高；
- AGPL-3.0 许可需要评估。

**结论**：不适合本期。

#### 4.3.5 ejabberd / XMPP

**优势**

- XMPP 是成熟的 IETF 标准，支持 presence、roster、消息扩展；
- ejabberd 在 Erlang/OTP 上经过大规模验证，提供移动可靠性层、推送、WebSocket/BOSH；
- 生态中有大量 XMPP 客户端库。

**代价**

- XML 协议冗长，移动端流量与解析成本高于 JSON；
- uni-app x 没有官方成熟的 XMPP SDK，需要自行封装或使用原生插件；
- XMPP 的 roster/花名册模型与“同小区默认好友”不一致，需要自定义扩展；
- Erlang 技术栈的运维门槛高；
- 移动推送（APNs/厂商通道）仍需自行集成。

**结论**：协议成熟，但与项目技术栈和产品模型不匹配。

#### 4.3.6 Centrifugo

**优势**

- Go 编写，专注实时消息网关，WebSocket 连接管理成熟；
- 语言无关，支持 Redis/NATS 等引擎做水平扩展；
- 频道订阅、存在性、历史消息等原语完善；
- Apache-2.0，部署相对简单。

**代价**

- 不是完整 IM：没有好友关系、会话、消息持久化、已读回执等业务语义；
- 需要额外的 token 鉴权与后端集成；
- 引入独立服务，增加一个部署单元；
- 对当前“1 对 1 + 自研业务表”的场景，收益不如直接使用现有 FastAPI WebSocket + Redis Pub/Sub。

**结论**：如果未来 WebSocket 连接规模成为瓶颈，可作为网关层候选；本期不引入。

#### 4.3.7 Tinode

**优势**

- 轻量 IM，Go 编写，支持单聊/群聊/已读；
- JSON over WebSocket 与 gRPC，客户端绑定多语言；
- 数据存储可选 MySQL/MongoDB/RethinkDB。

**代价**

- 服务端 GPL-3.0，商用需评估；
- 社区与生态规模小于 OpenIM/Matrix；
- 仍需要与现有用户、认证、内容审核体系打通；
- 公开资料对其稳定性的描述为“功能完整但仍有少量 bug”，需要自行验证。

**结论**：可作为备选，但不是当前最优。

#### 4.3.8 自研 FastAPI WebSocket

**优势**

- 与现有 `users/residents/certifications/conversations/messages` 无缝集成；
- 复用现有 JWT 鉴权、内容审核、举报、通知、审计；
- 技术栈统一（Python + PostgreSQL + Redis），团队熟悉；
- 可按业务需要精确实现“同小区默认好友”“双认证门禁”“拉黑”等规则；
- 部署简单，当前规模足够。

**代价**

- 需要自行实现消息可靠性、离线补偿、多实例广播、连接治理；
- 未来大规模群聊/音视频通话需要额外建设；
- 需要持续投入测试与运维。

**结论**：本期首选。通过合理的协议设计与 Redis Pub/Sub，可以覆盖当前及中期规模。

### 4.4 协议对比

| 协议/方案 | 传输 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| WebSocket + JSON | 全双工 TCP | 浏览器/移动端原生支持、低延迟、易调试、与现有代码一致 | 无内置消息语义，需自行设计 ACK/seq/离线 | 自有 App 的 1 对 1/小群聊 |
| XMPP | XML over TCP/WebSocket/BOSH | 标准成熟、presence/roster 完善、可扩展 | XML 冗长、客户端复杂、移动推送需额外集成 | 跨组织 IM、联邦通信 |
| MQTT | 发布/订阅 over TCP/WebSocket | 轻量、省电、QoS 0/1/2、适合弱网 | 无好友/会话/历史/已读语义，偏 IoT | 设备消息、推送通道 |
| Matrix | HTTP Sync + WebSocket | 开放标准、联邦、E2EE、VoIP | 协议重、部署重、模型复杂 | 跨组织协作、强隐私 |
| gRPC | HTTP/2 | 高性能、强类型、流式 | 浏览器/移动端直连需代理，调试成本高 | 内部服务间通信 |
| HTTP 长轮询 | HTTP | 兼容性最好 | 延迟高、连接开销大 | WebSocket 不可用时的降级 |

**结论**：

- 业务消息使用 **WebSocket + JSON**，HTTP REST 作为发送/拉取的兜底；
- 不引入 XMPP/MQTT/Matrix 作为主协议；
- 未来若需要与外部系统互通，可在网关层做协议适配，不改变内部消息模型。

### 4.5 选型结论（ADR）

**决策**：本期采用“自研轻量 IM + FastAPI WebSocket + PostgreSQL + Redis Pub/Sub”，不引入 OpenIM/Matrix/Rocket.Chat/Mattermost/ejabberd/Tinode。

**理由**：

1. 当前业务是单小区、1 对 1、文字/表情为主，完整 IM 套件的多数能力用不上；
2. 现有项目已经有用户、认证、会话、消息、内容审核、举报、通知、审计，引入外部 IM 会导致用户体系和消息存储双写；
3. 团队技术栈统一在 Python/FastAPI/PostgreSQL，运维成本最低；
4. 通过 `clientMsgId` 幂等、会话内 `seq`、服务端 ACK、离线补偿，可以满足微信式基础体验；
5. 未来规模增长时，可以在不改变客户端协议的前提下，将 WebSocket 网关替换为 Centrifugo 或迁移到 OpenIM。

**架构约束**：

- 消息以 PostgreSQL 为唯一权威存储；
- WebSocket 只负责实时推送，不承担消息持久化；
- 多实例通过 Redis Pub/Sub 广播，Redis 不可用时降级为单实例推送 + 客户端 HTTP 补偿；
- 协议层保持 `action/payload` JSON 信封，便于未来替换网关。

### 4.6 演进路径与触发条件

| 阶段 | 规模/需求 | 方案 |
| --- | --- | --- |
| 本期 | 单城市、单小区数千住户、1 对 1 文字/表情 | 自研 FastAPI WebSocket + PostgreSQL + Redis |
| 中期 | 多小区、日活 1 万~5 万、需要图片/语音 | 保持自研，增加对象存储、消息分表/归档、Redis 集群 |
| 后期 | 日活 5 万+、多地域、需要群聊/音视频/多端漫游 | 评估 Centrifugo 作为网关，或迁移 OpenIM；客户端协议保持不变 |
| 特殊需求 | 跨组织联邦、E2EE | 评估 Matrix；不建议在现有业务内自研 E2EE |

**迁移触发条件**（满足任一即启动评估）：

1. WebSocket 同时在线连接持续超过单实例 1 万；
2. 消息发送 P95 超过 500ms 且数据库优化无法解决；
3. 需要群聊、音视频通话、消息撤回/多端漫游等复杂 IM 能力；
4. 运维团队无法承担自研 IM 的持续维护；
5. 业务扩展到多城市、多租户，需要独立 IM 服务。

### 5.3 部署形态

**单实例（本期默认）**

- FastAPI 单进程 + PostgreSQL + Redis（可选）；
- `WsManager` 直接维护本机连接；
- 无 Redis 时，WebSocket 推送只在当前进程生效，客户端通过 HTTP 拉取补偿；
- 适合开发、测试、单小区试点。

**多实例（水平扩展）**

- 多个 FastAPI 实例部署在负载均衡后；
- WebSocket 连接按 `userId` 或随机分配到实例；
- 任一实例发送消息后，将推送事件发布到 Redis Pub/Sub；
- 所有实例订阅并只向本机连接推送；
- Redis 不可用时，消息仍落库，客户端通过重连补偿；实时性降级但不丢消息。

**Redis Pub/Sub 频道设计**

```text
频道：ws:push
消息：{
  "userId": 123,
  "action": "MSG_PUSH",
  "payload": { ... },
  "traceId": "..."
}
```

- 消息体只包含推送所需字段，不包含完整聊天历史；
- Pub/Sub 是“尽力而为”，丢失不影响数据一致性，因为 PostgreSQL 已持久化；
- 大规模时按 `userId` 哈希分片到多个频道，降低单频道压力。

### 5.5 关键设计决策

| 编号 | 决策 | 说明 |
| --- | --- | --- |
| D-01 | 默认邻居关系采用隐式推导，不物化 | 避免 N² 写入与一致性问题 |
| D-02 | 保留 `/friends` 路径，语义调整为“同小区认证邻居” | 减少移动端改动；新增子资源接口 |
| D-03 | 拉黑按“关系对”双向阻断 | 简化门禁，降低骚扰 |
| D-04 | 本期表情 = Unicode 表情，复用 TEXT | 零后端协议变更；大表情包后续用 `EMOJI` |
| D-05 | WebSocket 信封统一为 `action/payload` | 与移动端、详细设计一致；服务端兼容 `type/data` 一个版本 |
| D-06 | 消息以 PostgreSQL 为唯一权威 | WebSocket 只做推送，不做持久化 |
| D-07 | 未读使用读游标，不逐条更新消息状态 | 降低写放大 |
| D-08 | 多实例使用 Redis Pub/Sub | 轻量、与现有 Redis 配置一致 |
| D-09 | 认证失败使用 40304 | 与现有错误码体系一致，前端可引导认证 |
| D-10 | 新增 40305 表示“关系已阻断” | 区分普通无权限与拉黑/关系失效 |

### 6.2 表结构

#### 6.2.1 `friend_blocks`（新增）

```sql
CREATE TABLE friend_blocks (
    id           BIGSERIAL PRIMARY KEY,
    blocker_id   BIGINT NOT NULL REFERENCES users(id),
    blocked_id   BIGINT NOT NULL REFERENCES users(id),
    community_id BIGINT NULL REFERENCES communities(id),
    reason       VARCHAR(200) NOT NULL DEFAULT '',
    source       VARCHAR(16) NOT NULL DEFAULT 'CHAT',  -- CHAT/LIST/PROFILE/REPORT
    status       VARCHAR(16) NOT NULL DEFAULT 'ACTIVE', -- ACTIVE/RELEASED
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    released_at  TIMESTAMPTZ NULL,
    CONSTRAINT uq_friend_blocks_pair UNIQUE (blocker_id, blocked_id),
    CONSTRAINT ck_friend_blocks_self CHECK (blocker_id <> blocked_id)
);

CREATE INDEX ix_friend_blocks_blocked_status
    ON friend_blocks (blocked_id, status);
CREATE INDEX ix_friend_blocks_blocker_status
    ON friend_blocks (blocker_id, status);
```

说明：

- 同一对用户只保留一行；解除拉黑时更新 `status='RELEASED'`、`released_at`，再次拉黑时复用该行并重置状态。
- `community_id` 记录拉黑发生时的社区，便于审计；不参与关系判定。
- `reason` 可选，前端不强制填写；后台可用于风控分析。

#### 6.2.2 `friend_remarks`（新增）

```sql
CREATE TABLE friend_remarks (
    id         BIGSERIAL PRIMARY KEY,
    owner_id   BIGINT NOT NULL REFERENCES users(id),
    peer_id    BIGINT NOT NULL REFERENCES users(id),
    remark     VARCHAR(64) NOT NULL DEFAULT '',
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_friend_remarks_pair UNIQUE (owner_id, peer_id),
    CONSTRAINT ck_friend_remarks_self CHECK (owner_id <> peer_id)
```

说明：

- 备注只对 `owner_id` 可见；邻居列表返回 `remark` 优先于昵称展示。

### 6.3 关系判定 SQL

#### 6.3.1 邻居列表查询（分页）

```sql
WITH me AS (
    SELECT r.community_id
    FROM residents r
    JOIN users u ON u.id = r.user_id
    WHERE r.user_id = :me
      AND r.status = 'ACTIVE'
      AND r.certification_status = 'VERIFIED'
      AND u.status = 'ACTIVE'
      AND u.realname_status = 'VERIFIED'
    ORDER BY r.id DESC
    LIMIT 1
)
SELECT
    r.user_id            AS peer_id,
    u.nickname,
    u.avatar_key,
    r.building,
    r.identity_type,
    COALESCE(fr.remark, '') AS remark
FROM residents r
JOIN users u ON u.id = r.user_id
JOIN me ON me.community_id = r.community_id
LEFT JOIN friend_remarks fr
       ON fr.owner_id = :me AND fr.peer_id = r.user_id
WHERE r.user_id <> :me
  AND r.status = 'ACTIVE'
  AND r.certification_status = 'VERIFIED'
  AND u.status = 'ACTIVE'
  AND u.realname_status = 'VERIFIED'
  AND NOT EXISTS (
      SELECT 1
      FROM friend_blocks b
      WHERE b.status = 'ACTIVE'
        AND (
            (b.blocker_id = :me AND b.blocked_id = r.user_id)
            OR
            (b.blocker_id = r.user_id AND b.blocked_id = :me)
        )
  )
  AND (
      :keyword = ''
      OR u.nickname ILIKE '%' || :keyword || '%'
      OR r.building ILIKE '%' || :keyword || '%'
  )
ORDER BY COALESCE(NULLIF(fr.remark, ''), u.nickname), r.user_id
LIMIT :limit OFFSET :offset;
```

> 数据量大时改为 keyset 分页（`ORDER BY sort_key, user_id` + `WHERE (sort_key, user_id) > (:last_sort_key, :last_user_id)`），避免深分页。

#### 6.3.2 关系状态判定

```python
async def get_relation(db, me_id: int, peer_id: int) -> Relation:
    if me_id == peer_id:
        return Relation.SELF
    me = await get_eligibility(db, me_id)
    if not me.eligible:
        return Relation.ME_NOT_ELIGIBLE
    peer = await get_eligibility(db, peer_id)
    if not peer.eligible:
        return Relation.PEER_NOT_ELIGIBLE
    if me.community_id != peer.community_id:
        return Relation.NOT_SAME_COMMUNITY
    if await has_active_block(db, me_id, peer_id):
        return Relation.BLOCKED
    return Relation.FRIEND
```

`has_active_block` 同时检查两个方向：

```sql
SELECT 1
FROM friend_blocks
WHERE status = 'ACTIVE'
  AND (
      (blocker_id = :a AND blocked_id = :b)
      OR
      (blocker_id = :b AND blocked_id = :a)
  )
LIMIT 1;
```

### 6.4 数据迁移方案

新增 Alembic 迁移，建议拆成可重复执行的步骤：

1. 创建 `friend_blocks`、`friend_remarks`。
2. 为 `conversations` 增加 `pair_low_id`、`pair_high_id`、`last_message_type`、`last_sender_id`、`last_message_at`、`last_read_seq_a/b`、`cleared_at_a/b`。
3. 回填 `pair_low_id/pair_high_id`：
   ```sql
   UPDATE conversations
   SET pair_low_id = LEAST(user_a_id, user_b_id),
       pair_high_id = GREATEST(user_a_id, user_b_id)
   WHERE pair_low_id IS NULL OR pair_high_id IS NULL;
   ```
4. 去重 FRIEND 会话：
   - 按 `(pair_low_id, pair_high_id)` 分组；
   - 保留最早创建的会话；
   - 将重复会话的消息迁移到保留会话（更新 `messages.conversation_id`，重新分配 `seq`）；
   - 删除重复会话，或标记为 `ARCHIVED`（建议保留审计）。
5. 增加部分唯一索引与查询索引。
6. 为 `messages` 增加 `extra`、`read_at`、`deleted_at`，回填 `extra = '{}'`。
7. 创建 `messages` 幂等唯一索引前，先清理重复 `client_msg_id`：
   - 同一 `(conversation_id, sender_id, client_msg_id)` 只保留最早一条；
   - 其余标记 `deleted_at` 或迁移为新的 `client_msg_id`。
8. 旧好友数据：
   - `friends` 表保留，不删除；
   - `friend_requests` 中双方双认证同小区的 `PENDING` 记录批量置为 `ACCEPTED`，并写入通知；
   - 其他 `PENDING` 置为 `REJECTED`；
   - 发送迁移公告/站内信。
9. 旧好友申请入口下线：
   - 前端隐藏“好友申请”入口；
   - 仅当存在历史 `PENDING` 时展示一次“历史申请”入口，处理完自动隐藏。

**回滚**

- 代码回滚到旧版本时，新表/新列不影响旧逻辑；
- 旧 `Friend`/`FriendRequest` 数据仍在；
- 迁移脚本只做新增与回填，不删除旧数据；
- 若必须回滚关系语义，关闭 `NEIGHBOR_FRIENDS_V2` 开关，恢复旧好友申请入口。

### 6.5 Redis 键设计

| Key | 类型 | TTL | 用途 |
| --- | --- | --- | --- |
| `social:eligibility:{userId}` | String(JSON) | 300s | 双认证/小区缓存；认证变更时主动删除 |
| `social:neighbors:{userId}:{page}:{hash}` | String(JSON) | 60s | 邻居列表短缓存（可选） |
| `social:block:pair:{low}:{high}` | String | 300s | 拉黑关系缓存（可选） |
| `social:rate:msg:{userId}` | String/List | 60s | 消息频率限制 |
| `social:rate:search:{userId}` | String | 60s | 邻居搜索频率限制 |
| `ws:presence:{userId}:{deviceId}` | String | 90s | 在线状态（可选） |
| `ws:push` | Pub/Sub | — | 多实例推送广播 |

> 缓存必须可失效；涉及拉黑、认证变更、解除拉黑时，删除相关 key。若实现成本高，本期可以先不做缓存，直接用数据库查询。

### 6.6 数据保留与清理

| 数据 | 保留策略 | 说明 |
| --- | --- | --- |
| 好友会话与消息 | 默认 3 年 | 待法务确认；到期归档到冷存储或删除 |
| 物品会话 | 随订单保留策略 | 涉及交易凭证，建议更长 |
| 拉黑记录 | 保留 3 年 | 用于风控与审计 |
| 备注 | 随关系保留 | 解除拉黑后可保留 |
| 系统通知 | 1 年 | 现有通知体系策略 |
| 审计日志 | 按现有后台策略 | 拉黑/解除必须留痕 |

**清理任务建议**

- 每日低峰期归档 3 年前的消息到对象存储（Parquet/JSONL）；
- 清理无引用的会话（双方都清空且超过保留期）；
- 监控表大小，超过阈值提前分表/分区。

- 好友会话发送前校验关系：双认证、同小区、未拉黑；

| --- | --- | --- |

- 更新对应 `last_read_seq_a/b`；
- 可选：通过 WebSocket 向对方推送 `MSG_READ`（已读回执，P1）。

### 7.4 WebSocket 协议

#### 7.4.1 连接

```text
wss://api.example.com/api/v1/ws?token=<accessToken>&deviceId=<deviceId>
```

- 鉴权失败：关闭码 4401；
- 连接成功后服务端发送 `PONG {connected:true}`；
- 同一用户允许多设备连接，建议上限 5；
- 心跳：客户端每 30s 发送 `PING`，服务端回 `PONG`；连续 2 次未收到 PONG，客户端重连。

#### 7.4.2 信封

**统一格式**

```json
{
  "v": 1,
  "action": "MSG_SEND",
  "payload": {},
  "ts": 1731300000000
}
```

**兼容策略（一个版本）**

- 服务端读取时兼容 `action/payload` 与旧 `type/data`；
- 服务端发送统一使用 `action/payload`；
- 客户端同时兼容两种格式；
- 下一个版本移除 `type/data`。

#### 7.4.3 上行帧

| action | payload | 说明 |
| --- | --- | --- |
| `PING` | `{ "ts": 173... }` | 心跳 |
| `MSG_SEND` | `{ "clientMsgId": "c-1", "conversationId": "88", "type": "TEXT", "content": "你好", "extra": {} }` | 发送消息 |
| `MSG_READ` | `{ "conversationId": "88", "lastSeq": 101 }` | 上报已读 |
| `MSG_ACK` | `{ "messageId": "9001", "clientMsgId": "c-1" }` | 客户端确认收到推送 |

#### 7.4.4 下行帧

| action | payload | 说明 |
| --- | --- | --- |
| `PONG` | `{ "ts": 173..., "connected": true }` | 心跳响应 |
| `MSG_ACK` | `{ "clientMsgId": "c-1", "messageId": "9001", "seq": 101, "createdAt": 173... }` | 服务端发送成功回执 |
| `MSG_PUSH` | `{ "conversationId": "88", "message": { ...消息 DTO... } }` | 新消息推送 |
| `MSG_READ` | `{ "conversationId": "88", "peerLastReadSeq": 101 }` | 对方已读（P1） |
| `RELATION_CHANGED` | `{ "peerId": "1024", "state": "BLOCKED" }` | 拉黑/解除/认证变更 |
| `ERROR` | `{ "code": 40305, "message": "关系已阻断", "clientMsgId": "c-1" }` | 发送失败 |
| `NOTIFY` | `{ ... }` | 现有站内通知 |
| `ORDER_EVENT` | `{ ... }` | 现有订单事件 |
| `AUDIT_EVENT` | `{ ... }` | 现有质检事件 |

#### 7.4.5 发送时序

```
客户端                          服务端                         PostgreSQL/Redis
  │                              │                               │
  │ 1. 本地插入 SENDING 消息      │                               │
  │    (clientMsgId=c-1)          │                               │
  │                              │                               │
  │ 2. WS MSG_SEND ─────────────►│                               │
  │                              │ 3. 鉴权/关系/内容校验          │
  │                              │ 4. 幂等检查 ──────────────────►│
  │                              │ 5. seq 分配 + 插入消息 ────────►│
  │                              │ 6. 更新会话摘要/读游标          │
  │                              │ 7. commit                     │
  │                              │                               │
  │                              │ 8. Redis Pub/Sub（多实例）     │
  │                              │ 9. 本机/其他实例推送 MSG_PUSH  │
  │◄──── MSG_ACK (c-1, seq) ─────│                               │
  │ 10. 替换本地消息为 SENT       │                               │
  │                              │──── MSG_PUSH ────────────────►│ 对方在线
  │                              │                               │
  │ 11. 若 5s 未收到 ACK          │                               │
  │     HTTP POST 重试（同一 id） │                               │
  │                              │                               │
```

#### 7.4.6 断线补偿

1. 客户端为每个会话持久化 `lastSeq`（本地存储）。
2. 重连成功后：
   - 刷新会话列表；
   - 对当前打开的会话调用 `GET /conversations/{id}/messages?afterSeq={lastSeq}`；
   - 其他会话在进入时按需补偿。
3. 如果发现 `seq` 不连续（例如收到 105，但本地最后是 101），调用 `afterSeq=101` 补齐。
4. 客户端去重：优先按 `id`，其次按 `clientMsgId`。

### 7.5 错误码与用户提示

| code | 场景 | 前端提示 | 动作 |
| --- | --- | --- | --- |
| 40304 | 未完成双认证 | “完成实名认证与住户认证后，即可和邻居聊天” | 跳转认证中心 |
| 40305 | 已被拉黑/关系阻断 | “对方已将你加入黑名单，暂无法发送消息” | 禁用输入框 |
| 40301 | 非会话参与者 | “无权访问该会话” | 返回列表 |
| 40401 | 用户/会话不存在 | “内容不存在或已失效” | 返回列表 |
| 42201 | 内容违规 | “消息包含违规内容，请修改后再发送” | 保留输入 |
| 42901 | 频率限制 | “发送太频繁，请稍后再试” | 按钮冷却 10s |
| 40902 | 幂等键冲突 | “消息正在发送，请勿重复提交” | 忽略重复请求 |
| 50000 | 系统错误 | “服务暂时不可用，请稍后重试” | 保留本地消息，可重发 |

### 7.6 接口版本与兼容

- API 路径保持 `/api/v1`，通过新增字段/接口实现向后兼容；
- 旧 `GET /friends` 响应字段保持，新增字段不影响旧客户端；
- 旧 `POST /friends/requests` 保留一个版本，返回 410 或提示“已升级为默认邻居关系”；
- WebSocket 信封兼容一个版本；
- 移动端通过 `AppConfig`/远端开关控制是否展示新邻居 Tab 交互，便于灰度。

## 8. 消息可靠性设计

### 8.1 发送链路

好友消息支持两条发送链路：

1. **WebSocket 优先**：已连接且状态健康时，通过 `MSG_SEND` 发送；
2. **HTTP 兜底**：WebSocket 未连接、发送超时或返回错误时，通过 `POST /conversations/{id}/messages` 发送。

> **本期实现说明**：为保证失败可重试与幂等一致性，移动端默认使用 HTTP 发送，WebSocket 负责 `MSG_PUSH` 实时下行；`MSG_SEND` 上行通道已实现并保留，后续可在 ACK 超时补偿完善后切换为 WS 优先。

两条链路共用 `send_chat_message` 服务方法，保证：

- 同一 `clientMsgId` 幂等；
- 同一套内容审核；
- 同一套 seq 分配；
- 同一套推送逻辑。

### 8.2 幂等

**数据库层**

```sql
CREATE UNIQUE INDEX uq_messages_client_msg
    ON messages (conversation_id, sender_id, client_msg_id)
    WHERE client_msg_id <> '';
```

**服务层**

```python
existing = await db.scalar(
    select(Message).where(
        Message.conversation_id == conversation.id,
        Message.sender_id == sender.id,
        Message.client_msg_id == client_msg_id,
    )
)
if existing:
    return existing, False
```

**注意**

- 同一 `clientMsgId` 但内容不同：返回 40902，避免客户端逻辑错误；
- 旧客户端不传 `clientMsgId`：服务端生成 `srv-{uuid}`，不保证重发幂等；
- 新客户端必须传 `clientMsgId`（UUID v4）。

### 8.3 顺序与 seq

**分配策略**

```sql
UPDATE conversations
SET last_seq = last_seq + 1,
    last_message = :preview,
    last_message_type = :type,
    last_sender_id = :sender_id,
    last_message_at = now(),
    updated_at = now()
WHERE id = :conversation_id
RETURNING last_seq;
```

- PostgreSQL 行锁保证同一会话并发发送时 seq 唯一且递增；
- SQLite 测试环境使用事务 + 单写者即可；
- 不要使用 `SELECT max(seq)+1`，会有并发重复风险。

**客户端排序**

- 按 `seq` 升序；
- 本地乐观消息没有 seq，放在末尾；
- 收到服务端消息后按 `clientMsgId` 替换本地消息并写入 seq；
- 若 seq 缺口，触发 `afterSeq` 补偿。

### 8.4 ACK、超时与重发

| 阶段 | 客户端行为 |
| --- | --- |
| 发送 | 本地插入 `SENDING`，启动 5s 定时器 |
| 收到 `MSG_ACK` | 替换为 `SENT`，记录 `messageId/seq`，清除定时器 |
| 5s 未收到 ACK | 通过 HTTP 重试一次（同一 `clientMsgId`） |
| 仍失败 | 标记 `FAILED`，展示红色感叹号，点击可重发 |
| 重发 | 复用原 `clientMsgId`；若服务端已存在则返回原消息 |
| 收到 `ERROR` | 根据错误码展示提示；40305/40304 禁用输入 |

### 8.5 离线同步

**客户端持久化**

- `lastSeqByConversation: Record<conversationId, number>`；
- 未发送成功的 `pendingMessages`（含 `clientMsgId`、内容、会话）；
- 草稿 `draftByConversation`。

**同步流程**

```text
App 启动 / 重连成功
  │
  ├─ GET /conversations              刷新会话列表与未读
  │
  ├─ 当前会话：
  │    GET /conversations/{id}/messages?afterSeq=lastSeq
  │    合并、去重、排序
  │
  ├─ 其他会话：
  │    进入会话时再拉取
  │
  └─ 重发 pendingMessages（同一 clientMsgId）
```

**可选优化**

- `GET /conversations/sync?since={updatedAt}`：一次返回多个会话的增量消息；
- 对消息量大的用户，按会话懒加载，避免启动时拉取全部历史。

### 8.6 已读与未读

**读游标**

- `conversations.last_read_seq_a` / `last_read_seq_b`；
- 用户进入会话或滚动到最新消息时，上报 `lastSeq`；
- 服务端更新自己的游标。

**未读数计算**

```sql
SELECT count(*)
FROM messages
WHERE conversation_id = :cid
  AND sender_id = :peer_id
  AND seq > :my_last_read_seq
  AND deleted_at IS NULL;
```

**会话列表未读**

- 对每个会话计算上述 count；
- 数据量大时，可增加 `unread_count_a/b` 冗余字段，在发送/已读时增减；
- 本期建议先实时计算，后续按性能数据决定是否冗余。

**已读回执**

- 本期不强制展示“已读/未读”字样；
- 预留 `MSG_READ` 下行事件，P1 再展示。

> **兼容说明**：现有 `messages.status` 仍保留，用于兼容旧接口与按消息展示状态；**未读数以读游标为准**，不再逐条更新 `messages.status`，避免写放大。若需要展示单条“已读”，可在读游标更新后异步回填 `read_at`。

### 8.7 多端同步

- 同一用户多设备登录时，所有设备都收到 `MSG_PUSH`；
- 已读游标以服务端为准，任一设备上报后其他设备下次刷新即可同步；
- 发送消息的 `clientMsgId` 由发送设备生成，其他设备通过 `MSG_PUSH` 看到该消息；
- 不做设备间消息删除同步（清空聊天记录为本地行为，P1 再做服务端软清空）。

### 8.8 失败降级

| 故障 | 降级策略 |
| --- | --- |
| Redis 不可用 | 单实例本机推送；多实例时消息仍落库，客户端重连补偿 |
| WebSocket 不可用 | HTTP 发送/拉取；心跳失败后指数退避重连 |
| 数据库慢 | 消息发送超时返回 50301/50000；客户端保留本地消息并重试 |
| 内容审核服务不可用 | 使用本地关键词兜底；记录待审消息；必要时先发后审（需产品确认） |
| 推送服务不可用 | 站内通知兜底；下次打开 App 拉取未读 |

## 9. 内容安全与风控

### 9.1 文本审核

复用现有 `ai_audit_service`：

- `BANNED_KEYWORDS`：命中直接拒绝（42201），不落库；
- `SENSITIVE_PATTERNS`：命中允许发送，写入 `risk_flag`，客户端展示风险提示；
- 文本长度：1~500 字符；
- 空白/纯空格拒绝；
- 连续重复字符/链接过多：可增加规则，命中则风控标记。

### 9.2 表情与媒体

**本期（Unicode 表情）**

- 表情作为文本的一部分，随文本审核；
- 纯表情消息允许；
- 客户端可对“仅表情”的消息使用更大字号渲染。

**后续（大表情/图片/视频/语音）**

| 类型 | 审核 | 存储 | 限制 |
| --- | --- | --- | --- |
| `EMOJI` | 表情 ID 白名单 | 客户端内置/CDN | 仅允许平台表情包 |
| `IMAGE` | 图片内容安全 + 缩略图 | MinIO 私有桶 | ≤10MB，JPG/PNG/WebP |
| `VIDEO` | 视频抽帧审核 | MinIO 私有桶 | ≤100MB，≤60s，MP4 |
| `VOICE` | 语音转文字审核（可选） | MinIO 私有桶 | ≤60s，AAC/MP3 |

### 9.3 频率限制

| 维度 | 限制 | 实现 |
| --- | --- | --- |
| 单用户消息发送 | 20 条/分钟，200 条/小时 | Redis 滑动窗口；无 Redis 时进程内降级 |
| 单会话消息发送 | 60 条/分钟 | Redis |
| 邻居搜索 | 30 次/分钟 | Redis/进程内 |
| 创建会话 | 30 次/分钟 | Redis/进程内 |
| 拉黑/解除 | 30 次/分钟 | Redis/进程内 |
| WebSocket 连接 | 每用户最多 5 个设备 | 连接注册中心 |

超限返回 42901，并在响应头/`data` 中带 `retryAfter` 秒数。

### 9.4 举报与拉黑联动

- 会话页更多菜单提供“举报该用户”；
- 举报对象类型支持 `USER`、`CONVERSATION`、`MESSAGE`；
- 举报后可选“同时拉黑”；
- 后台举报工作台可查看上下文消息（需权限与审计）；
- 拉黑不自动举报，举报不自动拉黑，二者独立。

### 9.5 审计与留痕

必须审计的操作：

- 拉黑、解除拉黑；
- 设置/清除备注；
- 认证通过、冻结、撤销（现有）；
- 后台查看敏感会话（新增，按权限）；
- 消息删除/撤回（后续）。

审计字段：操作人、对象、动作、时间、来源 IP/设备、traceId、变更前后摘要。审计日志不记录完整消息内容，避免隐私泄露。

### 9.6 隐私保护

1. 邻居列表只展示昵称、头像、认证徽章、楼栋（可选）、身份类型（可选）；
2. 不展示手机号、身份证、详细门牌、订单信息；
3. 楼栋展示默认开启还是关闭需产品确认；建议提供“在邻居列表展示我的楼栋”开关（P1）；
4. 搜索只支持昵称/备注/楼栋，不支持手机号搜索；
5. 接口返回 404 而非 403，避免枚举用户；
6. 消息内容不写入访问日志；错误日志只记录 `conversationId`、`messageId`、`traceId`；
7. 数据导出/注销时按隐私政策处理聊天记录。

| `fetchEligibility()` | 拉取好友资格 |
| `fetchNeighbors(reset?)` | 分页拉取邻居列表 |

#### 10.5.3 数据流

```
页面 ──► store ──► service ──► api ──► request
  ▲        │
  │        └──► ws.service（事件）
  │
  └── 响应式更新
```

- 页面不直接调用 `uni.request`；
- WebSocket 事件由 `App.uvue` 或 `social.store` 统一订阅；
- 避免多个页面重复订阅导致重复处理；
- Store 中的消息列表按 `seq` 排序，本地消息无 seq 时置底。

### 10.6 网络与异常处理

| 页面卸载 | 取消未完成请求，保留草稿/待发消息 |

#### 11.2.4 `assert_can_message`

```python
async def assert_can_message(
    db: AsyncSession, sender: User, conversation: Conversation
) -> None:
    peer_id = (
        conversation.user_b_id
        if conversation.user_a_id == sender.id
        else conversation.user_a_id
    )
    peer = await db.get(User, peer_id)
    if not peer:
        raise ApiError(ERR_NOT_FOUND, "对方用户不存在", 404)
    if conversation.type == "FRIEND":
        relation = await get_relation(db, sender.id, peer_id)
        if relation == Relation.BLOCKED:
            raise ApiError(ERR_RELATION_BLOCKED, "你们已互相拉黑，无法发送消息", 403)
        if relation != Relation.FRIEND:
            raise ApiError(ERR_NOT_VERIFIED, "完成实名认证与住户认证后才能发送邻居消息", 403)
    # ITEM 会话保留原实名校验；拉黑同样阻断
    if await has_active_block(db, sender.id, peer_id):
        raise ApiError(ERR_RELATION_BLOCKED, "你们已互相拉黑，无法发送消息", 403)
```

#### 11.2.5 `send_chat_message`

在现有基础上增加：

2. `type` 白名单校验；

4. 原子分配 `seq`；

#### 11.2.6 `mark_read`

### 11.3 事务与并发

- 消息发送在一个事务内完成：校验 → 幂等 → seq 分配 → 插入 → 更新会话 → 审计；
- `UPDATE conversations ... RETURNING last_seq` 行锁保证并发安全；
- 拉黑/解除拉黑在一个事务内完成：写 `friend_blocks` + 审计；
- 认证变更事件通过 Outbox 异步处理缓存失效与关系通知；
- 避免在事务内调用外部服务（内容审核、推送）；先审核后落库，推送在 commit 后执行。

### 11.4 事件与 Outbox

现有项目已有 `workers/outbox_relay.py`。建议新增事件：

| 事件 | 触发 | 消费 |
| --- | --- | --- |
| `CertificationApproved` | 认证通过 | 删除资格缓存；可选通知同小区 |
| `CertificationFrozen` | 认证冻结/撤销 | 删除资格缓存；将会话置为只读；推送 `RELATION_CHANGED` |
| `FriendBlocked` | 拉黑 | 删除关系缓存；推送 `RELATION_CHANGED` |
| `FriendUnblocked` | 解除拉黑 | 删除关系缓存；推送 `RELATION_CHANGED` |
| `ResidentLeftCommunity` | 住户迁出 | 删除资格缓存；关系失效 |

> 本期如果 Outbox 消费者不完善，可先同步处理关键路径（拉黑、认证变更），缓存失效用短 TTL 兜底。

### 11.5 多实例 WebSocket

**方案**

```python
class WsManager:
    async def push(self, user_id: int, action: str, payload: dict) -> int:
        # 1. 本机推送
        delivered = await self._push_local(user_id, action, payload)
        # 2. 多实例广播
        if settings.redis_url:
            await redis.publish("ws:push", json.dumps({
                "userId": user_id,
                "action": action,
                "payload": payload,
            }))
        return delivered
```

- 每个实例启动时订阅 `ws:push`；
- 收到广播后调用 `_push_local`；
- 本机已推送的消息可通过 `instanceId` 去重，避免重复；
- 单实例模式下跳过 Redis。

**连接治理**

- 每用户最多 5 个连接；
- 连接空闲 90s 无心跳则关闭；
- 单帧最大 64KB；
- 发送队列上限 100 条，超过断开慢消费者；
- 记录连接数、推送失败数、平均延迟。

### 11.6 性能优化

| 问题 | 优化 |
| --- | --- |
| 邻居列表慢 | `residents(community_id, certification_status, status)` 索引；分页；短缓存 |
| 会话列表慢 | `user_a_id/user_b_id + updated_at` 索引；必要时 UNION 两次查询 |
| 未读数慢 | 读游标 + `messages(conversation_id, seq)` 索引；后续可冗余计数 |
| 消息拉取慢 | `(conversation_id, seq)` 索引；分页；限制 50 条 |
| 发送并发 | 原子 `UPDATE ... RETURNING`；避免 `max(seq)+1` |
| 推送扇出 | Redis Pub/Sub；按用户哈希分片 |
| 内容审核慢 | 本地关键词先行；外部服务异步兜底；设置超时 |

### 11.7 安全设计

| 风险 | 对策 |
| --- | --- |
| 越权读取会话 | 每次请求校验 `user.id in (user_a_id, user_b_id)` |
| 越权发送消息 | 校验参与者 + 关系 + 拉黑 |
| 枚举用户 | 非邻居/无会话用户返回 404；搜索限频 |
| 拉黑绕过 | 所有发送入口（HTTP/WS）统一调用 `assert_can_message` |
| 重放/重复消息 | `clientMsgId` 幂等 + 唯一索引 |
| 刷消息 | 频率限制 + 内容审核 |
| 敏感信息泄露 | 日志脱敏；不返回手机号/地址 |
| 恶意图片/文件 | 后续媒体上传做类型/大小/病毒扫描 |
| 后台偷看聊天 | 权限控制 + 审计日志 |

### 13.5 安全测试

- 未登录/过期 Token 访问所有接口；
- 非会话参与者读取/发送消息；
- 伪造 `conversationId`、`peerId`；
- 拉黑后通过 HTTP/WS 双通道发送；
- 枚举用户（不同小区、非邻居）；
- 消息内容注入（XSS/SQL 注入/超长文本）；
- 频率限制绕过；
- 敏感信息泄露（日志、响应）；
- 后台无权限查看会话。

## 14. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- |
| 默认邻居列表暴露全小区住户 | 隐私投诉 | 中 | 不展示手机号/门牌；楼栋展示开关；拉黑；举报；隐私政策说明 |
| 小区住户过多导致列表/查询慢 | 体验下降 | 中 | 分页、索引、搜索、按楼栋筛选、短缓存 |
| 拉黑语义与微信不一致引发误解 | 用户困惑 | 中 | 产品文案明确“双方均无法发送”；客服培训 |
| 认证状态漂移（`users.realname_status` 与认证单不一致） | 误放/误拦 | 中 | 统一判定函数；数据修复任务；认证变更同步 |
| WebSocket 帧格式修复影响现有客户端 | 消息不可用 | 高 | 服务端双格式兼容一个版本；灰度；回归测试 |
| 会话唯一约束迁移失败 | 重复会话/数据错乱 | 中 | 先备份；迁移脚本幂等；去重脚本先在测试库演练 |
| Redis 不可用导致多实例推送失败 | 实时性下降 | 中 | 消息落库；客户端补偿；监控告警 |
| 消息量增长导致表膨胀 | 查询变慢 | 低/中 | 保留策略、归档、分区、索引优化 |
| 内容审核误杀 | 用户投诉 | 中 | 关键词可配置；人工复核；申诉入口 |
| 拉黑被滥用 | 社交体验差 | 低 | 拉黑上限；审计；举报联动 |
| 旧好友申请数据迁移遗漏 | 用户困惑 | 中 | 迁移校验；历史入口保留一个版本 |
| 认证撤销导致交易沟通中断 | 交易纠纷 | 中 | 物品会话保留但只读；客服/系统通知兜底 |
| 多设备消息重复/乱序 | 体验问题 | 中 | 按 `id/clientMsgId` 去重；按 `seq` 排序；补偿 |
| 表情在不同平台渲染不一致 | 视觉差异 | 低 | 使用系统 emoji 字体；真机测试；后续统一贴纸 |
