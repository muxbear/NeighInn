## 1. 引言

### 1.1 编写目的

本文档基于《邻里小栈需求规格说明 v1.1》与《邻里小栈UIUE设计设计规范-移动端 v1.0》，对移动端（C 端业主）进行**概要设计**——明确系统的总体架构、技术选型、模块划分、关键业务流程、接口契约与数据模型，作为后续**详细设计**与**编码实现**的指导蓝图。

预期读者：架构师、移动端开发工程师、后端开发工程师、测试工程师、DevOps 工程师。

### 1.2 文档范围

**本文档覆盖**：

- 移动端整体架构设计与技术选型
- 功能模块划分与模块间关系
- 关键业务流程的时序设计
- 与服务端的接口契约（移动端视角）
- 本地数据模型、状态管理、路由导航、缓存策略
- 关键技术方案：IM 即时通信、担保支付、AI 质检、地图距离计算、推送
- 非功能设计：性能、安全、兼容、可观测性

**不在本文档范围内**：详细代码实现（类/方法级）、UI 视觉细节标注（见 UI/UX 规范）、服务端内部实现（见服务端概要设计）、Web 端设计（见 Web 端概要设计）。

## 2. 总体设计

### 2.1 设计目标与约束

#### 2.1.1 设计目标

| 编号 | 目标 | 度量 |
| --- | --- | --- |
| G-01 | 核心交易路径最短 | 浏览→下单→支付 ≤ 3 步 |
| G-02 | 首屏性能 | 4G 网络下首页白屏时间 ≤ 2s |
| G-03 | IM 实时性 | 消息端到端延迟 ≤ 500ms（同网），断线重连 ≤ 3s |
| G-04 | AI 质检体验 | 端侧预检 ≤ 2s，服务端质检 ≤ 60s 且进度可视 |
| G-05 | 中老年可用性 | 长辈模式一键切换，关键操作双确认 |
| G-06 | 资金安全 | 支付全链路可视化，敏感信息不落本地明文 |

#### 2.1.2 约束

| 编号 | 约束 | 来源 |
| --- | --- | --- |
| C-01 | 微信小程序（首选）/ Android App / iOS App 三形态交付 | SRS 2.2 |
| C-02 | 最低支持 Android 8.0 / iOS 13 | SRS 2.2 |
| C-03 | 移动端不提供后台管理功能 | SRS 3.2 |
| C-04 | 支付仅对接持牌机构（微信支付/支付宝），资金托管在服务端 | SRS BR-11 |
| C-05 | 所有敏感信息传输加密、本地加密存储、展示脱敏 | SRS 9.2 |

| 形态 | 定位 | 登录方式 | 支付 | 推送 |
| --- | --- | --- | --- | --- |
| 微信小程序 | 拉新与轻量使用首选 | 微信授权 + 手机号绑定 | 仅微信支付 | 订阅消息 |

| iOS App | 完整体验与深度用户 | 手机号 + 微信 | 微信/支付宝 | APNs + 极光 |

### 2.3 技术选型

#### 2.3.1 核心决策

**决策：采用 uni-app（Vue 3 + TypeScript）作为主技术栈，一套代码编译到微信小程序 / Android / iOS 三端。**

| 备选方案 | 评估结论 |
| --- | --- |
| uni-app（Vue3 + TS） | **✅ 选中**。三端覆盖成本最低，Vue 生态成熟，团队上手快，插件市场完善（支付/推送/IM 均有成熟插件） |
| Taro（React） | 能力相当，但社区 IM/支付类插件生态略弱于 uni-app |
| 原生三端分别开发 | 体验最优但成本约 3 倍，v1.1 周期内不可行；作为长期演进备选 |
| Flutter | 小程序端仍需二次开发，双栈维护成本高 |

> **演进预留**：若后续 App 端对性能/体验提出更高要求（v2.0），可将 App 端迁移至 Flutter/原生，小程序端保留 uni-app，服务端 API 不变，迁移成本可控。

#### 2.3.2 技术栈清单

| 维度 | 选型 | 版本基线 | 说明 |
| --- | --- | --- | --- |
| 框架 | uni-app（Vue 3） | HBuilderX 4.x / CLI 3.x | Composition API + `<script setup>` |
| 语言 | TypeScript | 5.x | 全量 TS，strict 模式 |
| 状态管理 | Pinia | 2.x | 官方推荐，DevTools 友好 |
| 网络请求 | 拦截器封装的 `uni.request` | — | 统一封装：Token 注入、错误码分发、重试、取消 |
| UI 组件 | 自建组件库（按 UI/UX 规范）+ uni-ui 补充 | — | 设计 Token 直接映射为 SCSS 变量/CSS 变量 |
| 样式 | SCSS + CSS Variables | — | Token 双轨：编译期变量 + 运行期 CSS 变量（支持深色模式切换） |
| IM 长连接 | WebSocket（`uni.connectSocket` 封装） | — | 心跳、重连、消息队列、断网缓存 |
| 地图 | 高德地图（App SDK / 小程序 map 组件） | — | 路径规划与耗时由服务端代理调用，端侧只展示 |
| 支付 | `uni.requestPayment`（微信/支付宝渠道） | — | 服务端统一下单，端侧仅拉起收银台 |
| 推送 | 小程序：订阅消息；App：极光推送 | — | 统一推送服务层抽象 |
| 图片 | `uni.chooseImage` + 端侧压缩（canvas / 原生插件） | — | 上传前压缩至 ≤ 300KB，长边 ≤ 2000px |
| 端侧预检 | 小程序：Canvas 采样 + 启发式算法；App：原生轻量模型插件 | — | 模糊/过暗/过曝快速检测，≤ 2s |
| 埋点 | 自建上报 SDK（批量+失败重传） | — | 对接服务端埋点接口 |
| 单元测试 | Vitest | — | 纯逻辑层（utils/service/store）测试 |
| E2E | 小程序自动化（miniprogram-automator）+ App 云真机 | — | 核心链路回归 |

#### 2.3.3 跨端差异处理

| 差异点 | 处理方式 |
| --- | --- |
| 支付渠道 | 条件编译 `#ifdef MP-WEIXIN` / `#ifdef APP-PLUS` 分支处理 |
| 登录方式 | 小程序走微信授权；App 走手机号验证码 + 微信 SDK |
| 推送 | 小程序订阅消息；App 极光推送，统一封装为 `NotifyService` |
| 地图组件 | 小程序用 `<map>`；App 用高德原生插件，统一封装为 `MapService` |
| 文件系统 | 小程序 `wx.fileSystemManager`；App plus.io，统一封装 `FileService` |
| 安全区/刘海屏 | 统一使用 `--status-bar-height`、`--window-bottom` CSS 变量适配 |

## 3. 技术选型补充说明

> 第 2.3 节已给出选型结论，本章补充**选型验证要点**，评审时逐项确认。

| 主题 | 验证要点 | 风险与对策 |
| --- | --- | --- |
| uni-app 小程序包体积 | 主包 ≤ 2MB（微信限制），采用分包：首页/附近主包，发布/交易/社交/钱包分包 | 分包预下载策略：登录后预下载 trade 分包 |
| App 端支付插件 | 微信/支付宝 App 支付 SDK 在 uni-app 上的证书与签名配置 | 提前 2 周完成三平台（微信开放平台/支付宝开放平台/应用商店）开发者账号与签名申请 |
| IM 自建 vs 云服务 | 自建 WebSocket（服务端统一网关）成本可控、与业务会话表强一致 | v1.1 自建；若峰值并发超预期，v1.2 评估接入云 IM（如腾讯云 IM） |
| 端侧预检收益 | 小程序端无原生 AI 运行时的方案可行性（Canvas 采样 + 亮度/拉普拉斯方差启发式） | 端侧预检只做"快速拦截明显废片"，**不做终审**，终审一律服务端 |
| 高德地图配额 | 路径规划 API 由服务端代理调用并缓存（SRS 8.2），端侧不直连 | 端侧仅展示服务端返回的距离/耗时，配额压力在服务端 |

### 4.3 各模块设计

#### 4.3.1 账号与认证模块（auth）

**职责**：手机号/微信登录、实名认证（OCR+人脸）、业主证明提交、认证状态机管理。

**认证状态机**（与 SRS 4.3 对齐）：

```
NOT_LOGIN → LOGGED_IN_UNVERIFIED → VERIFYING → VERIFIED_UNOWNER
                                    │
                                REJECTED(可重提)
VERIFIED_UNOWNER → SUBMITTING_PROOF → PENDING_AUDIT → VERIFIED_OWNER
                                        │
                                    REJECTED(可重提，3次转人工)
VERIFIED_OWNER ⇄ FROZEN（违规冻结，在售物品自动下架）
```

**关键设计**：

| 设计点 | 方案 |
| --- | --- |
| Token 管理 | JWT 存于 `uni.setStorageSync`（小程序）/ EncryptedPreferences（App）；Access Token 2h，Refresh Token 30d，401 自动静默续期 |
| 实名信息 | 端侧**不缓存**身份证号/姓名原文，仅缓存脱敏展示串（`330***********1234`） |
| 人脸核验 | 对接第三方 SDK（小程序端用 H5 核验页跳转），结果由服务端确认，端侧不持有核验凭证 |
| 认证进度轮询 | 提交后进入"审核中"页面，30s 间隔轮询 + 订阅消息/推送兜底通知 |

#### 4.3.2 物品模块（item）

**职责**：发布表单、照片管理、AI 质检交互、详情展示、我的发布管理。

**发布表单领域模型**：

```typescript
interface ItemDraft {
  title: string;                    // 2-30 字
  category: Category;               // 两级类目
  transactionType: TransactionType; // MONETARY | FREE_GIFT | BARTER
  price?: number;                   // MONETARY 必填；FREE_GIFT 固定 0
  barterExpect?: BarterExpect;      // BARTER 必填：结构化标签+自由文本
  conditionLevel: ConditionLevel;   // 五档成色
  qualityDesc: string;              // ≥ 20 字
  photos: ItemPhoto[];              // 3-12 张，含顺序
  video?: UploadedMedia;            // 可选 ≤60s ≤100MB
  invoicePhotos?: UploadedMedia[];  // 可选凭证
  expectTradeTime?: string[];       // 期望交易时段
  aiAudit?: AuditReport;            // 质检结果
  status: DraftStatus;              // DRAFT | AUDITING | REJECTED | SUBMITTED
}
```

**关键设计**：

| 设计点 | 方案 |
| --- | --- |
| 草稿自动保存 | 表单变更防抖 1s 后写入本地存储（`uni.setStorage`），恢复发布时提示还原 |
| 照片上传 | 先压缩（长边 2000px / ≤300KB）→ 服务端换取预签名 URL → 直传对象存储 → 回传 key；上传队列并发 3，失败重试 3 次 |
| 拍摄引导 | 首次发布显示引导浮层（整体照→细节照→缺陷照），按 UI 规范 P-51 |
| 质检交互 | 提交后不阻塞页面，进入"质检进度页"：步骤列表（图像质量→图文一致性→合规→汇总）+ 轮询（2s 间隔）或 WebSocket 推送进度 |
| 一物多卖防护 | 下单成功后由**服务端**将物品置为"已预约"，端侧在详情页轮询状态并在被占用时置灰交易按钮（40901 错误码兜底） |

#### 4.3.3 交易与订单模块（trade）

**职责**：三种交易方式的订单创建、预约验货、验货确认、互评、纠纷提交。

**订单领域模型**：

```typescript

  id: string;
  itemId: string;

```

**三种交易方式的差异化策略**（策略模式）：

interface TradeStrategy {

**关键设计**：

| 设计点 | 方案 |
| --- | --- |
| 状态同步 | 订单列表/详情进入时拉取 + WebSocket 订单事件推送（状态变更主动下发）+ 下拉刷新兜底 |

| 验货确认 | 双按钮"验货满意（大） / 验货不满意（小）"，不满意必选原因；确认操作需二次确认弹窗（长辈模式同） |
| 评价引导 | 交易完成后跳转评价页，未评价项在"我的-订单"持续提示 |

## 5. 关键业务流程设计

### 5.1 注册→实名→业主认证→发布 全流程

```
┌────────┐  验证码/微信授权  ┌────────────┐  OCR+活体  ┌────────────┐
│ 启动App │ ───────────────▶ │  实名认证   │ ─────────▶ │ 业主证明提交 │
└────────┘                  └────────────┘            └─────┬──────┘
                                                            │ 选择小区+上传材料
                                                      ┌─────▼──────┐
                                                      │ 待平台审核  │
                                                      │ (轮询+推送) │
                                                      └─────┬──────┘
                                                  ┌─────────┴─────────┐
                                              通过│                   │驳回
                                          ┌───────▼───────┐   ┌───────▼───────┐
                                          │ 绑定小区生效   │   │ 展示驳回原因   │
                                          │ 解锁发布能力   │   │ 可重提(≤3次)  │
                                          └───────┬───────┘   └───────────────┘
                                                  │
                                          ┌───────▼───────┐
                                          │   发布物品     │
                                          └───────┬───────┘
                                                  │
                                          ┌───────▼───────┐
                                          │  AI 质检流水线  │（见 5.2）
                                          └───────┬───────┘
                                                  │
                                          ┌───────▼───────┐
                                          │ 上架至本小区商店│
                                          └───────────────┘
```

**时序要点**：

1. 登录成功 → 建立全局状态（user.store）→ 建立 WebSocket 连接 → 拉取未读数/订阅消息授权引导；
2. 认证状态每次冷启动 + 关键操作（发布/交易）前从服务端校验，不依赖本地缓存状态做权限判断（服务端强校验为准，SRS AC-03）。

### 5.2 发布 + AI 质检流程

```
用户填写表单
   │ 照片选择 → 端侧压缩 → 端侧预检(≤2s)
   │        ├─ 明显废片 → 即时提示重拍（不阻塞继续上传）
   │        └─ 通过 → 进入上传队列
   │ 草稿自动保存(防抖1s)
   ▼
点击【提交发布】
   │ 前置校验：表单完整性 / 照片≥3 / 描述≥20字
   │ 服务端创建物品(草稿态) + 生成 traceId
   ▼
质检进度页（轮询 2s 或 WS 推送）
   │ STEP1 图像质量 → STEP2 图文一致性 → STEP3 合规检测 → STEP4 汇总决策
   │ 单件端到端 ≤ 60s，超时转人工（NF-04）
   ▼
┌──────────┬───────────────┬──────────────┐
│   PASS   │     FAIL      │ NEED_HUMAN   │
│  展示报告 │  展示驳回原因   │  提示审核中   │
│  进入待复核│  +改进建议     │  结果推送通知 │
│  (高置信快车道│ 一键返回修改 │              │
│   可免复核) │              │              │
└──────────┴───────────────┴──────────────┘
```

**端侧预检算法**（小程序实现示例）：

| 检测项 | 算法 | 阈值 |
| --- | --- | --- |
| 过暗/过曝 | 下采样 64×64 计算亮度均值/直方图 | 亮度均值 < 40 或 > 220 提示 |
| 模糊 | 拉普拉斯变换方差（Canvas 卷积近似） | 方差 < 阈值提示"照片模糊" |
| 分辨率不足 | 原始尺寸检查 | 短边 < 720px 提示 |

> 端侧预检结论只提示不阻断（用户可坚持提交），最终以服务端 AI 质检为准（BR-04）。

### 5.3 货币交易（担保支付）流程

```
买家在详情页点击【担保支付购买】
   │
   ▼
创建订单 POST /orders  (幂等键 clientOrderId)
   │ 服务端校验：物品在架/非自买/BR-08 物品未占用 → 锁定物品
   │ 返回订单(CREATED_PENDING_PAY, 30min 支付倒计时)
   ▼
收银台页
   │ 选择渠道(微信/支付宝) → 服务端统一下单 → 端侧拉起支付
   ├─ 支付成功回调/主动查询 → ESCROWED → 进入预约验货页
   └─ 超时未支付 → 服务端自动取消并解锁物品
   ▼
预约验货页（时间+地点，可改期）
   ▼
线下当面验货 → 双方在移动端操作
   ├─ 双方【验货满意】→ DEAL_CONFIRMED → 服务端放款 → COMPLETED
   ├─ 任一方【不满意+原因】→ REFUNDING → 原路退款 → REFUNDED(关闭)
   └─ 发起纠纷 → DISPUTING → 平台调解 → MEDIATED(关闭)
   ▼
互评 → 信用分累积 → 订单闭环
```

**端侧要点**：

1. 支付结果以**服务端查询+异步通知双通道**确认，不信任支付 SDK 的本地回调作为最终状态；
2. 放款自动确认（买家 72h 未操作）由服务端定时任务处理，端侧仅展示倒计时提示；
3. 订单状态页展示资金流向时间轴（UI 规范 7.5 S-01/S-02）。

### 5.4 免费赠与 / 物品互换流程

```
赠与：买家点击【申请免费领取】 → 创建订单(APPLIED)
      → 卖家确认(PENDING_CONFIRM→CONFIRMED, 48h 超时自动取消)
      → 预约验货 → 双方确认交割 → COMPLETED → 互评

互换：买家点击【发起物品互换】 → 选择自己的在架物品/补充说明(端侧校验该物品已过AI质检)
      → 创建订单(APPLIED, 含双方物品快照)
      → 卖家确认 → 预约验货 → 双方确认交割 → COMPLETED → 互评
```

**端侧要点**：互换申请页需清晰展示"我用什么换什么"双物品对照卡片；任一方物品在预约期间被其他订单占用时，服务端拒绝创建并返回 40901。

### 5.5 IM 消息收发流程

```
发送方                                    接收方
  │                                         │
  │ 构造消息(clientMsgId)                    │
  │ ▼                                       │
  │ 本地消息表落库(SENDING) → 渲染气泡        │
  │ ▼                                       │
  │ WebSocket 发送 ────────────────────────▶ │ 服务端内容安全审核(A-09)
  │                     ├─ 违规 → 发送方撤回+提示│
  │                     └─ 合规 → 存储分发 ───▶ │ 在线：WS 下发 → 落库 → 渲染 → ACK
  │ ◀──────────────────── ACK(SENT/已读回执) ── │ 离线：推送(订阅消息/极光) → 深链进入
  │ 更新状态 SENT → READ                       │
```

### 5.6 冷启动流程

```
App 启动
  │ 1. 读取本地 Token（无 → 登录页）

```

## 6. 接口设计

### 6.1 通用约定

| 项目 | 约定 |
| --- | --- |
| 协议 | HTTPS + RESTful + JSON（与服务端网关统一，见 SRS 8.3） |
| 认证 | `Authorization: Bearer <accessToken>`；`X-Refresh-Token` 用于续期 |
| 幂等 | 写操作请求头 `X-Idempotency-Key`（UUID），端侧生成 |
| 分页 | `page` / `pageSize`（默认 20，最大 50），响应含 `total`、`hasMore` |
| 时间戳 | Unix 毫秒（UTC），端侧格式化为本地时间 |
| 错误码 | 复用 SRS 附录 14.3：40001/40101/40301/40302/40901/42201/42901/50000 |
| 统一响应 | `{ code, message, data, traceId }`；`code === 0` 为成功 |

### 6.3 WebSocket 协议设计

连接地址：`wss://api.neighinn.example/ws?token=<accessToken>&deviceId=<uuid>`

**帧格式**（JSON 文本帧）：

```json
// 上行
{ "action": "MSG_SEND",  "payload": { "clientMsgId": "u1", "conversationId": "c1", "type": "TEXT", "content": "你好" } }
{ "action": "MSG_ACK",   "payload": { "clientMsgId": "u1" } }
{ "action": "MSG_READ",  "payload": { "conversationId": "c1", "lastMsgSeq": 1024 } }
{ "action": "PING",      "payload": { "ts": 1731300000000 } }

// 下行
{ "action": "MSG_PUSH",    "payload": { "seq": 1025, "message": { "...": "ChatMessage" } } }
{ "action": "ORDER_EVENT", "payload": { "orderId": "o1", "event": "STATUS_CHANGED", "status": "ESCROWED" } }
{ "action": "AUDIT_EVENT", "payload": { "itemId": "i1", "step": 2, "result": "PROCESSING" } }
{ "action": "PONG",        "payload": { "ts": 1731300000000 } }
```

**约定**：

| 项目 | 规则 |
| --- | --- |
| 心跳 | 30s 间隔 PING；连续 2 次未收到 PONG 判定断线 |
| 重连 | 指数退避 1s→2s→4s→8s→…→60s；重连成功后按会话 `lastSeq` 增量同步 |
| 消息序号 | 服务端全局/会话级 `seq` 单调递增，端侧据此去重与排序 |
| 降级 | WS 不可用时消息发送走 HTTP 兜底接口，接收依赖轮询（30s）+ 推送 |

## 8. 状态管理设计

### 8.1 Store 划分（Pinia）

| Store | 职责 | 持久化 |
| --- | --- | --- |
| `user.store` | 登录态、认证状态机、用户信息、未读数 | Token + profile |
| `app.store` | 主题（深/浅）、长辈模式、业务配置、全局 Toast | settings |
| `item.store` | 首页/附近信息流、筛选条件、我的发布列表 | home_feed_cache |
| `order.store` | 订单列表（按 Tab）、订单详情缓存、支付中订单 | 无（信任服务端） |
| `social.store` | 会话列表、各会话未读数、好友列表、好友申请 | im_conv_list |

### 8.2 数据流原则

```
用户操作 → 页面调用 composable/service → api/store → 服务端
                │                                    │
                └── store 更新（唯一可信来源）◀── 响应/推送
                              │
                    页面响应式渲染（单向数据流）
```

- **单一数据源**：跨页面共享的状态一律放 store；页面私有状态用组件本地 `ref`；
- **服务端为准**：物品状态、订单状态、钱包余额等交易关键状态，本地缓存仅做展示兜底，操作前后强制与服务端对账；
- **事件驱动**：WebSocket 下行的 `ORDER_EVENT` / `MSG_PUSH` / `AUDIT_EVENT` 由 `App.vue` 全局接收后分发到对应 store，页面只订阅 store，不直连 WS；
- **乐观更新**：仅用于收藏/点赞等低风险操作（失败回滚）；支付、验货确认、放款等资金相关操作**不做乐观更新**。

## 11. 关键技术方案

### 11.1 IM 即时通信

| 方面 | 方案 |
| --- | --- |
| 通道 | 自建 WebSocket（服务端统一网关），协议见 6.3 |
| 可靠性 | clientMsgId 幂等 + 本地消息表 + ACK 确认 + seq 排序去重 + 失败重发（手动） |
| 安全 | WSS + Token 鉴权（连接时校验）；消息内容服务端审核（A-09） |
| 性能 | 消息列表虚拟渲染（长会话按 50 条分页加载）；图片消息走压缩上传 |
| 通知 | 端内红点 + 未读数；端外：小程序订阅消息 / App 极光；点击深链跳会话 |

### 11.2 担保支付

| 方面 | 方案 |
| --- | --- |
| 下单 | 端侧请求 `/payments/prepay` → 服务端调用持牌渠道统一下单 → 返回拉起参数 → `uni.requestPayment` |
| 结果确认 | 支付 SDK 本地回调仅作 UI 反馈；最终以 `GET /payments/{orderNo}/status` 轮询（2s×15 次）+ 服务端渠道回调为准 |
| 收银台 | 按 UI 规范 6.8.1：大金额、服务保障三条、56dp 主按钮、"资金由持牌机构托管"提示 |
| 异常 | 拉起失败/取消：保留订单倒计时；支付中杀进程：重进收银台先查询订单状态再决定是否重新拉起；防重复支付由服务端幂等保证 |
| 退款/放款展示 | 订单时间轴展示资金流向（买家→托管→卖家），退款原路返回进度可见 |

### 11.3 AI 质检（端侧协同）

| 方面 | 方案 |
| --- | --- |
| 端侧预检 | 亮度/模糊/分辨率启发式检测（见 5.2），仅提示不阻断，≤ 2s |
| 服务端质检 | 服务端 AI 流水线（SRS 第 7 章 A-01~A-07），端侧轮询进度或接收 `AUDIT_EVENT` 推送 |
| 进度展示 | 4 步骤进度列表 + 每步结果；60s 超时提示"转人工审核中" |
| 结果处理 | PASS → 待复核（高置信快车道直接上架）；FAIL → 驳回原因卡片 + 一键返回修改；申诉入口固定 |
| 报告展示 | 底部弹窗：维度得分条 + 风险标签 + 置信度 + 建议，含 traceId（申诉凭证） |

### 11.4 距离与耗时（对应 SRS 8.2）

| 方面 | 方案 |
| --- | --- |
| 数据来源 | 服务端计算（小区坐标对 + 高德路径规划 + 缓存），端侧**不直连**地图 API |
| 展示 | 列表卡片："约 850m · 步行 12 分"；详情页：步行/骑行/驾车三行（UI 规范 7.4） |

### 11.5 推送与通知

| 端 | 通道 | 触发场景 |
| --- | --- | --- |
| 小程序 | 订阅消息（一次性订阅） | 认证结果、订单状态变更、IM 离线消息、物品过期提醒 |

### 13.2 发布流程

| 端 | 流程 |
| --- | --- |
| 微信小程序 | 代码审查 → 体验版（test/staging）→ 提交审核（微信支付类目资质：二手交易需确认类目要求）→ 全量发布；分包更新使用差量热更新 |

## 14. 代码规范与工程化

| 主题 | 规范 |
| --- | --- |
| 代码风格 | ESLint（@vue/eslint-config-typescript）+ Prettier + Stylelint；提交前 husky + lint-staged 强制 |
